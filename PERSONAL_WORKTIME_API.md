# Общий API личного табеля: смены и настройки

2026-10-27. Реализовано локально, не выложено. Веб-календарь и APK к новому API пока не подключены.

## Общий контракт

Контроллер `Api/PersonalWorkTimeController`, общий файл `routes/personal-worktime.php`.
Два префикса с одинаковыми JSON-ответами:
- веб: `/api/worktime/v2` под существующими auth/device/barrier/CSRF;
- APK: `/api/mobile/worktime` под Sanctum + EnsureActiveApiUser, без веб-барьеров.

Оба пути проверяют активность. Владелец — только текущий пользователь, даже для администратора.
Успешные ответы имеют `Cache-Control: no-store, private`. Применён throttle 60/min для группы,
дополнительно 20/min для записывающих маршрутов. Новых ролей и изменений доступа к документам нет.

| Метод и путь после префикса | Назначение |
|---|---|
| GET `/month?month=YYYY-MM` | Производная сводка, связки, отдых и предупреждения |
| GET `/settings?month=YYYY-MM` | Эффективные настройки и редакция записи данного месяца |
| PATCH `/settings/{month}` | Частичное изменение настроек с месяца YYYY-MM |
| POST `/shifts/preview` | Предварительный расчёт новой смены без сохранения |
| POST `/shifts` | Создание с operation_id (UUID) |
| GET `/shifts/{id}` | Только своя смена v2 с revision и снимком |
| POST `/shifts/{id}/preview` | Предварительный расчёт редактирования |
| PUT `/shifts/{id}` | Полное замещение редактируемых полей собственной смены v2 |

Поля времени — московское локальное YYYY-MM-DD HH:mm, не ISO с Z/offset.
PUT передаёт всю карточку: shift_date, started_at, ended_at и используемые необязательные
поля break_duration, shift_code, route_id, start_location, end_location, segments.
Пропущенные необязательные поля очищаются; перерыв по умолчанию 0, отсутствие участков означает линию.
Тарифы, снимок, суммы, владелец и версия расчёта из тела запроса не принимаются.
DELETE пока нет. Чужая или старая v1-смена на новых маршрутах возвращает 404.

## Редакции и повторная отправка

Миграция `2026_10_27_110000_add_work_time_mutation_receipts` добавляет revision (default 1)
в work_shifts и work_time_month_settings, а также work_time_mutations.
Последняя — операционные квитанции идемпотентности, не отдельный журнал аналитики.

Для создания требуется operation_id. Для PUT также expected_revision >=1;
для PATCH настроек expected_revision >=0. Ноль означает, что записи настроек именно этого
месяца ещё нет. Для preview существующей смены нужен expected_revision, но не UUID.

`WorkTimeMutationService` блокирует текущего пользователя, сравнивает action и hash
нормализованного payload, выполняет изменение и сохраняет ответ в одной транзакции.
Область UUID общая для всех операций пользователя. Иной payload/action под тем же UUID →409.
Повтор успешной операции возвращает исходный JSON-ответ, даже если запись позже изменена.
Повтор не начисляет деньги, не увеличивает revision и не пишет второй аудит.

Новый UUID не позволяет обойти устаревшую редакцию: expected_revision всё равно сравнивается.
При ошибке валидации/пересечении/чужой записи транзакция откатывает изменение и квитанцию.
После неопределённого сетевого результата клиент повторяет замороженное тело и тот же UUID.
После 409 клиент должен загрузить актуальную запись, а не автоматически подставлять её редакцию.
После получения позднего старого ответа можно GET-запросом получить текущую карточку.

## Снимок ставок и перенос месяца

Обычное редактирование сохраняет прежний calculation_snapshot и считает по нему.
Изменение настроек само по себе не переписывает сохранённые смены.
Только явный `refresh_snapshot=true` в preview/PUT выбирает свежие эффективные настройки
для месяца смены. При переносе в другой месяц этот флаг обязателен; preview и сохранение
используют одинаковый путь подготовки данных. Изменения ограничены существующей строкой
с увеличением revision; операция и существующий work_shift.saved позволяют отследить правку.

При сохранении проверяются пересечения с другими сменами обоих поколений.
Старый WorkShiftController теперь тоже блокирует пользователя и возвращает 409, если v1-запись
попадает на дату или время уже существующей v2. Старый календарь не может тихо создать
параллельную запись поверх нового табеля. Остальные v1-расчёты не менялись.

## Настройки

Редактируются только line_rate_kopecks, reserve_rate_kopecks, surface_rate_kopecks,
evening_percent, night_percent и rest_dates. Ставки — целые копейки, суммы нормализуются
к integer, проценты ограничены 0–100. Границы суток и нормативы отдыха пользователь не меняет.
rest_dates — уникальные YYYY-MM-DD только выбранного месяца, не более 31; пустой массив очищает список.

Ставки и проценты наследуются с даты изменения в последующие месяцы до следующего override.
Например, ставка с октября действует и в ноябре, если ноябрь не задаёт свою ставку.
Предшествующие месяцы и снимки сохранённых смен не меняются. Выходные не наследуются.
revision относится к записи выбранного месяца, не к совокупности всех прошлых overrides;
PATCH должен отправлять изменённые поля, сохраняя остальные наследуемыми.
Изменение исторического override влияет на будущие новые preview/снимки, но не на уже сохранённые.

GET не создаёт запись: возвращает effective settings и revision=0 при отсутствии override.
Редактор получает/сохраняет данные под блокировкой пользователя. Идентичная новая запись
операции с теми же значениями не увеличивает редакцию и не создаёт лишнее событие.

Событие `work_time.settings_saved` отдельно согласовано владельцем 2026-10-27:
ClickHouseService после COMMIT, user_id, month, changed_fields — без ставок, сумм и значений.
Смены переиспользуют `work_shift.saved`. Квитанции не являются дополнительными событиями ClickHouse.

## Проверки и ограничения

439 PHP-тестов, 2312 assertions прошли, включая обязательные проверки доступа и маршрутов.
На изолированном PostgreSQL 17: 38 тестов табеля / 202 assertions и реальные гонки:
create UUID/overlap/conflicting payload, повтор PUT, разные PUT с одной revision,
два PATCH при expected_revision=0. PostgreSQL после проверок остановлен.

Проверены общий веб/мобильный контракт, реальные Sanctum-токены, устройство/барьер веба,
неактивный пользователь, чужие ID, UUID/revision, откат неуспешной правки, отсутствие ставок
в аудите, наследование будущих ставок без наследования выходных и явный перенос месяца.

calculation_complete остаётся false. Настройки классности/выслуги/премии/удержаний,
неподтверждённые формулы и полный перенос всех ветвей CNTSMEN этим API не объявляются готовыми.
Следующий блок — веб-календарь, мобильные экраны и клиентская обработка очереди/конфликтов.

Перед будущей выкладкой обязательны обе миграции 2026_10_27_100000 и 110000.
