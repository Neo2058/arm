# Следующий этап: шифрование персональных данных

Согласованное направление — 29 октября 2026. Реализация начинается после текущего
укрепления хоста/runtime. В этом документе нет включения шифрования или миграции.

## Цель и границы

Защитить идентифицирующие данные при краже дампа/backup или отдельной БД.
Шифруем имена/фамилии/отчества, телефоны, номера прав управления и даты рождения.
Не меняем формулы расчётов, роли и канонический интерфейс карусели.
Данные смен/сумм можно оставить открытыми по решению владельца, но это не делает
всю оставшуюся БД анонимной: табельные номера, email, Telegram/device/IP identifiers,
связи и редкие события позволяют повторную идентификацию. Нужна инвентаризация.
Пароли продолжают храниться как стойкие хеши, а не обратимо зашифрованные строки.

## Карта данных перед разработкой

- users.name/email; user_profiles.phoneNumber/driverRoot/birth_date/tab_number,
  instructor/additional_notes и связанные свободные поля.
- arm_personnel.full_name/phone_primary/phone_secondary/source_data: импортируемый
  JSON тоже может содержать открытые копии. Импорт DBF и повторный импорт учесть.
- phone_contacts.name/phone: общая база телефонов и запрет дублей сохраняются.
- Telegram linkage, наряды/PDF/DBF/экспорт, квизы/комментарии, ClickHouse details,
  ActionLog, уведомления, cache, поиск, мобильные черновики, backup и старые snapshots.
- Для каждой копии определить: шифрование/маскирование/исключение/срок хранения.
  Изменение схемы/событий ClickHouse требует отдельного согласования.

## Архитектура на стенде

1. Существующие числовые/UUID связи оставить; отдельные поля ciphertext + key version.
   Использовать проверенное AEAD, случайные nonce и контекст пользователя/поля.
2. Envelope encryption: ключи данных шифруются главным ключом внешнего KMS/Vault.
   Главный ключ не экспортируется в runtime; ключи аутентификации транспорта/mTLS
   независимы от ключей шифрования данных. Не писать собственный криптопротокол.
3. Сервер ключей отделить от production. Сервер Telegram подходит только после
   аудита: процесс relay не должен читать ключи/токены KMS, управлять KMS или backup.
   Скрытые имена файлов не считаются защитой. Отдельные администратор/политики/аудит.
4. Доступ к расшифровке по короткоживущим полномочиям, минимальной области и лимитам;
   журнал без открытых персональных данных, обнаружение массового чтения и отзыв.
5. Резервирование KMS, шифрованные backups, независимое хранение recovery-материала,
   проверенное восстановление и правила недоступности KMS обязательны до rollout.

## Совместимость и производительность

- Для равенства/уникальности телефона и email нужны нормализация и независимый
  keyed blind index; обычный hash телефонов не защищает от перебора.
  Утечка равенства при таком поиске — явное ограничение, не анонимизация.
- Поиск по части ФИО/телефона, сортировка, отчёты, Filament и импорты требуют
  отдельного решения; не отправлять plaintext в Meilisearch по умолчанию.
- Ограниченный кеш ключей в памяти может снизить задержку, но увеличивает окно
  доступа при компрометации. Сроки выбрать после измерения p95/p99 web/APK.
- Сервер, легитимно расшифровывающий данные, при RCE может использовать эти же
  полномочия. Root может читать память/перехватывать вывод. Внешний KMS снижает
  риск кражи ключей и помогает отзыву, но не гарантирует защиту работающего runtime.

## Порядок реализации и приёмка

- [ ] Завершить текущий hardening; проверить внешние backups и восстановление.
- [ ] Инвентаризация всех идентификаторов/копий и согласование точного охвата.
- [ ] Стенд внешнего KMS и политики, включая аварийное восстановление.
- [ ] Один вертикальный сценарий профиля с совместимостью web/APK, без production.
- [ ] Поиск/уникальность телефонов, импорты, отчёты и редактирование по ролям.
- [ ] Миграция небольшими партиями с контрольными суммами, версионированием ключей
      и совместимым откатом; не оставлять открытые копии в параллельных полях.
- [ ] Тест кражи дампа без ключей, отказа/компрометации KMS, ротации, восстановления,
      отказов сети, целостности ciphertext и запрета доступа чужого пользователя.
- [ ] Отдельное согласование production-cutover после отчёта и измерения нагрузки.

Критерий готовности: выбранные поля и их копии не читаются из дампа без независимого
доступа к ключам; функции приложения и ограничения доступа сохранены. Не обещать
«нечитаемость данных при любом взломе сервера».
