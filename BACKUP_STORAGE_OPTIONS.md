# Внешние резервные копии ARM: варианты и требования

Подготовлено 30 октября 2026. Это предложение для выбора, не включённая услуга.
Ничего не заказано, учётные записи не созданы, данные провайдерам не передавались.

Предлагаю начать с отдельного S3-хранилища с Object Lock и шифрованием архивов
до загрузки. У него меньше задач администрирования, чем у второго Linux-сервера.
Аккаунт хранилища должен быть независим от production, с MFA и отдельным доступом
владельца. Закрытый ключ расшифровки и административные права не хранить на production.

## Варианты

| Вариант | Почему подходит | Что придётся обслуживать |
|---|---|---|
| Yandex Object Storage | Есть блокировка версий объектов и режимы retention; требуется versioning | Настроить bucket, IAM, retention и контроль расходов; проверить запрет удаления upload-ключом. [Документация Object Lock](https://yandex.cloud/ru/docs/storage/concepts/object-lock) |
| Selectel S3 | Есть Object Lock, versioning и управление доступом | Проверить выбранный пул/регион, bucket policy, неизменяемость и восстановление. [Документация Object Lock](https://docs.selectel.ru/s3/buckets/object-lock/) |
| Отдельный backup-сервер у другого провайдера | Можно принимать новые копии через append-only сервис; production не должен иметь SSH/root к хранилищу | Обновления ОС, диски, мониторинг, отдельная административная учётная запись и обслуживание retention. [rest-server append-only](https://github.com/restic/rest-server/blob/master/README.md) запрещает изменение/удаление существующих данных через этот режим; root самого backup-хоста остаётся доверенной стороной |
| Компьютер владельца / отключаемый диск | Дополнительная копия вне production, удобна для аварийного доступа | Компьютер может быть выключен, нужны шифрование диска, расписание и контроль свежести. Как единственное автоматическое хранилище не предлагается |

Для S3 предлагается загружать завершённые зашифрованные архивы под уникальными
именами с manifest. Не подключать restic к Object Lock вслепую: блокировки временных
объектов, удаление/prune и retention требуют отдельной проверки совместимости.
Цены не рассчитаны: зависят от региона, объёма, числа запросов и скачивания при аварии.
Перед подключением проверить регион размещения персональных данных и условия сервиса.

## Обязательные требования

1. Ключ production может создавать копии в выделенном prefix, но не удалять версии,
   менять политики bucket, обходить retention, сокращать блокировку или управлять
   аккаунтом. Проверить это реальными отрицательными тестами на тестовой копии.
2. Object Lock/versioning настроить и проверить до первой полезной загрузки.
   Governance требует строгого ограничения обхода; compliance сильнее ограничивает
   удаление и может удерживать ошибочно загруженные данные до истечения срока.
   Режим выбрать после теста на отдельном bucket, не экспериментировать на единственных копиях.
3. Шифрование до загрузки, проверка целостности, SHA-256 manifest, TLS.
   Восстановительный ключ хранится у владельца вне production и отдельно резервируется.
   Для архивов можно использовать шифрование открытым ключом: production хранит
   получателя, а закрытый ключ для восстановления ему не нужен. Формат/инструмент
   выберем перед реализацией. Потеря закрытого ключа означает потерю доступа к архивам.
4. Предлагаемая начальная retention — 30 дней. Автоочистка только отдельной ролью
   хранилища после истечения блокировки, без прав удаления на production.
   Новое хранение ещё не применено. Технические system logs ClickHouse не архивировать:
   их отдельная месячная политика сохраняется.
5. Внешний контроль возраста последней завершённой копии, размера, свободного места,
   пропавшего heartbeat и неуспешного восстановления. Успешный cron не равен копии.
   Канал алертов/получателя настроить отдельным шагом; сообщения сейчас не отправлялись.
6. Ежемесячный тест с загрузкой копии ИЗ внешнего хранилища, расшифровкой и запуском
   изолированного приложения/БД/объектов. Записать измеренное время восстановления.
7. Оплата/MFA/recovery codes и контакты провайдера доступны владельцу даже при
   недоступности production. Telegram relay не должен получать административные ключи backup.

## Что сохранять

- PostgreSQL: согласованный логический дамп, версии схемы, отдельно необходимые роли/
  grants без переноса чрезмерных runtime-привилегий. Дамп пользователей не содержит PDF.
- MinIO: объекты, metadata и bucket configuration/policies. Нужна точка восстановления,
  согласованная с PostgreSQL: например, краткое согласованное ограничение записей или
  проверенная схема сохранения версий объектов. Простая пара копирований в разное время
  не гарантирует согласованность при загрузке/удалении файлов.
- ClickHouse: user_actions и другие действительно нужные прикладные таблицы, не весь
  растущий каталог system logs. Сначала инвентаризация, затем согласованный способ backup;
  схемы/TTL/события здесь не менялись.
- Laravel storage: пользовательские вложения и нужные private/public файлы. Кеши,
  временные PDF и framework cache отделить от пользовательских файлов после проверки.
- Секреты восстановления: APP_KEY, per-service env, TLS, ключи подписи/другие незаменимые
  ключи — только внутри зашифрованного архива с отдельным доступом, никогда в Git.
- Compose overlays, host hardening/cron/systemd configuration, commit и image digests.
  Для восстановления при недоступности registry нужен также проверенный способ получить
  образы/артефакты; один digest не сохраняет образ.
- Redis/Meilisearch: определить, что можно перестроить. Потеря кеша/индекса и сессий
  отличается от потери PostgreSQL; не обещать сохранение незавершённых задач без проверки.

Не делать tar работающих PostgreSQL/MinIO/ClickHouse volumes как единственную копию.
Backup одного компонента не равен восстановлению приложения целиком.

## Объём и расписание для старта — предложение

На 30 октября: PostgreSQL около 14 МБ в работающей БД, проверенный custom dump
487 370 байт; MinIO 112 МБ; Laravel storage 6,1 МБ. ClickHouse volume 7,4 ГБ включает
технические логи — это не целевой размер пользовательской аналитики.

30 полных ежедневных копий текущих PostgreSQL/MinIO/storage — ориентировочно 4 ГБ
до учёта роста, версий объектов, аналитики, конфигурации и образов. Это оценка, не
измерение готового зашифрованного архива. Для начала можно предусмотреть 20–50 ГБ
с бюджетным оповещением; образам и полному образу ОС нужна отдельная оценка.

Предлагается: полный согласованный набор ежедневно и перед опасными выкладками;
PostgreSQL дополнительно каждый час. Целевые потери по времени — до 1 часа для БД,
до суток для полного набора, пока не согласована более частая схема файлов. Это
не действующие гарантии и не единый согласованный RPO для всех компонентов.
Целевое время полного восстановления определить после практического теста.

## Что нужно выбрать владельцу

1. S3 (Yandex/Selectel) или отдельный backup-сервер; регион и бюджет.
2. После выбора — создать независимый аккаунт с MFA. Подготовим точную политику и
   тестовый bucket; ключи передавать через приватный env-файл, не через чат.
3. Проверить upload/запрет удаления/расшифровку на тестовых данных, затем подключить
   production и расписание. Отдельно сохранить ключ восстановления на компьютере/
   в менеджере секретов и независимой офлайн-копии.

До этого внешние автоматические копии не настроены. Проверенный локальный дамп —
полезная контрольная точка, но остаётся на том же хосте и разделяет его риски.
