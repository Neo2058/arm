# Два Telegram-бота ARM

Дата: 2026-10-23. Production и Telegram пока не изменены. Ни один реальный API-запрос или сообщение ботам
из этой работы не отправлялся: запросы проверялись через Http::fake().

## План

- [x] Общий генератор месячного ключа с прежним алгоритмом.
- [x] Одноразовая привязка активного пользователя ARM к Telegram ID, отвязка, ограничения доступа.
- [x] Публичный webhook ключевого бота с проверкой secret_token, выдача только в личном чате.
- [x] Разделение токенов бота ключей и бота оповещений.
- [x] Уведомления о заявках, устройствах, входах и попытках скачивания; ошибки Telegram не ломают приложение.
- [x] Диагностика/настройка через artisan, безопасный relay без токена в исходниках и без журналирования содержимого.
- [x] Тесты безопасности и регрессия доступа; инструкция BotFather, env, migrations, webhook и проверка доставки.
- [ ] Настройка настоящих ботов и production оператором, browser/device smoke и проверка фактической доставки.

## Найдено

- `/telegram/webhook` был внутри auth/device/barrier и CSRF, поэтому Telegram не мог штатно вызвать его.
- `/key` не проверял регистрацию, привязки Telegram ID к пользователю не существовало.
- Один токен использовался для пользовательских ответов и административных уведомлений.
- Входы логировались в ClickHouse, но не доставлялись боту оповещений.
- В старом deploy-relay.sh обнаружен токен: перевыпустить его через BotFather, даже после удаления из кода.
- Relay журналировал секрет и сообщения; его Docker-образ не устанавливал PHP cURL.

## Принятые решения

Бот ключей выдаёт ключ только в личном чате активному пользователю, привязанному из ARM одноразовой
ссылкой на 10 минут. Username/ФИО/email из сообщения не являются подтверждением регистрации.
Страница привязки доступна после входа, до device/barrier, иначе возникнет замкнутый круг получения ключа.
Прочие защищённые разделы сохраняют проверки устройств и барьера.
Ключ общий месячный, четыре значения 0–3; алгоритм и сохранение прохождения барьера в сессии не меняются.
Групповая публикация самого ключа отключается, чтобы обход проверки пользователя был невозможен.
Второй бот отправляет административные уведомления в заданный личный чат или закрытую группу.
Webhook для второго бота не требуется. Платёжные webhook не входят в эту задачу.
Ответ бота ключей отдаётся в теле HTTP-ответа webhook (`method: sendMessage`): Telegram
доставляет сообщение даже если сервер ARM не может открыть исходящее HTTPS к api.telegram.org.
Административные уведомления по-прежнему требуют исходящий доступ или relay.

## 1. Что сделать в Telegram

1. В официальном **@BotFather** отозвать токен из старого скрипта: `/revoke`, выбрать соответствующего бота.
   Удаление строки из git не отзывает токен и не удаляет его из истории. Старый токен больше нигде не использовать.
2. Создать два разных бота через `/newbot` (либо перевыпустить существующих):
   - **ARM — ключ доступа**, например `your_arm_keys_bot`;
   - **ARM — уведомления администратору**, например `your_arm_alerts_bot`.
   Это примеры имён: username должен быть свободен. Сохранить токены в защищённом месте, не в git и не в чате с AI.
3. Для бота ключей выполнить `/setjoingroups` → выбрать бота → **Disable**.
   Отключить inline mode, если ранее включали. Через `/setcommands` задать:

   ```text
   start - Привязка к учётной записи ARM
   key - Ключ доступа на текущий месяц
   help - Как получить доступ
   ```

4. Если старый бот уже был в группах, убрать его оттуда. Бот не публикует ключ в группе даже при получении update.
5. Для уведомлений выбрать один вариант:
   - личный чат администратора: открыть второго бота и нажать **Запустить**;
   - закрытая группа администраторов: создать её, добавить только доверенных сотрудников и второго бота.
     Разрешить боту отправку сообщений. Права администратора ему не нужны, если группа разрешает писать участникам.
     Privacy mode можно оставить включённым; для определения ID послать `/start@имя_бота_уведомлений` в группе.
6. Пользователям выдавать адрес страницы ARM `/account/telegram`, а не общую ссылку с токеном привязки.

Telegram-бот не становится невидимым по username. «Закрытый» здесь означает проверку ARM на сервере:
посторонний увидит только инструкцию входа, но не получит ключ. Имя в Telegram, номер телефона, членство в группе
или знание email пользователя не дают доступа.

Источники: [создание и управление ботами](https://core.telegram.org/bots/features#botfather),
[команды и проверка авторизации](https://core.telegram.org/bots/features#commands),
[одноразовые start-ссылки как транспорт](https://core.telegram.org/bots/features#deep-linking).
Одноразовость и срок действия реализованы в ARM, не в Telegram.

## 2. Настроить приложение на сервере

В `.env` production задать новые значения (примеры ниже — названия полей, без настоящих секретов):

```dotenv
TELEGRAM_KEY_BOT_TOKEN=ТОКЕН_БОТА_КЛЮЧЕЙ
TELEGRAM_KEY_BOT_USERNAME=your_arm_keys_bot
TELEGRAM_KEY_WEBHOOK_SECRET=СЛУЧАЙНЫЙ_СЕКРЕТ_НЕ_ТОКЕН_БОТА
TELEGRAM_NOTIFICATIONS_BOT_TOKEN=ДРУГОЙ_ТОКЕН_БОТА_УВЕДОМЛЕНИЙ
TELEGRAM_NOTIFICATIONS_CHAT_ID=
TELEGRAM_NOTIFICATIONS_QUEUE_CONNECTION=database
```

Username указывать **без @**. `TELEGRAM_KEY_WEBHOOK_SECRET` — отдельная случайная строка из 32–256 латинских
букв/цифр/символов `_` и `-`. Например, локально сгенерировать `php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'`
и скопировать результат в защищённый `.env`. Не использовать токен бота как webhook secret.

Для прямого соединения убрать старые `TELEGRAM_RELAY_URL`, `TELEGRAM_RELAY_SECRET`,
`TELEGRAM_KEY_RELAY_URL`, `TELEGRAM_KEY_RELAY_SECRET`. `TELEGRAM_API_URL` оставить стандартным HTTPS Telegram.
Новые notification-поля имеют fallback на старые TELEGRAM_BOT_TOKEN/CHAT_ID, но для двух ботов лучше заполнить
явные новые поля и убрать старые секреты. TELEGRAM_GROUP_ID не используется для выдачи ключа.

`APP_URL` должен указывать на фактический канонический HTTPS-домен (с правильным www, если он используется).
Сертификат должен быть действительным. Reverse proxy/WAF должен пропускать `POST /telegram/webhook`
и заголовок `X-Telegram-Bot-Api-Secret-Token` без редиректа на login, CAPTCHA или HTML challenge.
Остальные web/Livewire POST сохраняют CSRF; исключён только точный URI Telegram.

**BARRIER_SALT сохранить прежним.** Не генерировать новую соль при этой выкладке: иначе текущий ключ изменится.
Генератор в боте и проверка на сайте теперь используют один MonthlyAccessKey с прежним алгоритмом и
серверной временной зоной. В начале следующего месяца он вычислит новый ключ при запросе, cron для этого не нужен.

## 3. Выкладка через репозиторий

1. Сохранить текущий release SHA, backup БД, `.env` и предыдущие assets. Выкладывать только проверенный release.
   В рабочем дереве могут быть независимые изменения — не применять git reset --hard и не публиковать их автоматически.
2. Установить зависимости по lock-файлам как в SECURITY_DEPENDENCIES.md. Для новых Blade-элементов собрать `npm run build`.
3. В согласованное окно maintenance выполнить внутри app новую аддитивную миграцию:

   ```bash
   docker compose -f docker-compose.prod.yml exec app php artisan migrate --force --path=database/migrations/2026_10_23_120000_create_telegram_links.php
   ```

   Она создаёт `telegram_accounts` и `telegram_link_tokens` в основной БД. Привязка одного пользователя к одному
   Telegram ID защищена уникальными ограничениями; link token хранится только как SHA-256 и заменяется при повторной выдаче.
4. Обновить `.env`, очистить кеш, перезапустить app и восстановить кеш **после** перезапуска:

   ```bash
   docker compose -f docker-compose.prod.yml exec app php artisan optimize:clear
   docker compose -f docker-compose.prod.yml restart app
   docker compose -f docker-compose.prod.yml exec app php artisan optimize
   ```

   Перезапуск app не заменяет restart существующего worker. Для database notifications нужен отдельный worker ниже.
5. Снять maintenance, проверить страницу привязки в браузере. Не удалять существующие сессии и не менять SESSION_DOMAIN.

Проверки приложения перед release: `php -d memory_limit=256M vendor/bin/phpunit` и `npm run build`.
Первый прогон большого полного набора упёрся в локальные 128 MiB; Docker проекта уже задаёт 256 MiB.
Контейнерная сборка самого relay и браузерный smoke требуют проверки оператором.

## 4. Определить chat_id бота уведомлений

После `/start` во втором боте (или команды в закрытой группе) выполнить:

```bash
docker compose -f docker-compose.prod.yml exec app php artisan telegram:manage notifications --updates
```

Команда показывает getMe и только ID/типы чатов, не содержимое сообщений и не токены.
Если у старого бота уже стоит webhook, `getUpdates` работать не будет. Для бота **уведомлений** его можно убрать:

```bash
docker compose -f docker-compose.prod.yml exec app php artisan telegram:manage notifications --clear-webhook --updates
```

Записать нужный `chat_id` в `TELEGRAM_NOTIFICATIONS_CHAT_ID`, сохранив знак `-` для группы, очистить/восстановить
config cache и перезапустить worker после изменения env. Не делать --clear-webhook для работающего бота ключей.

```bash
docker compose -f docker-compose.prod.yml exec app php artisan telegram:manage notifications --test
```

Это одна намеренная тестовая отправка, выполняется оператором. Успех означает принятие сообщения Telegram API,
но получатель ещё должен убедиться, что сообщение пришло в правильный закрытый чат.

## 5. Установить webhook бота ключей

```bash
docker compose -f docker-compose.prod.yml exec app php artisan telegram:manage key --webhook
docker compose -f docker-compose.prod.yml exec app php artisan telegram:manage key
```

Первая команда вызывает setWebhook с отдельным secret_token и allowed_updates=[message], вторая проверяет
getMe/getWebhookInfo без изменения настроек. Если username не совпадает с токеном или оба токена одинаковы,
команда завершится ошибкой. Настройку повторить при смене токена/домена/webhook secret.
Старый webhook бота уведомлений и новый webhook ключей принадлежат разным токенам.

Секретный заголовок проверяется до обработки данных. Только личный chat с chat.id=from.id допускается к командам;
группы, сообщения от ботов и пересланные команды не получают ключ. Лимит — 10 ответов на отправителя в минуту.
Cache должен быть общим для экземпляров приложения (например, Redis); dedup update_id хранится сутки.
При временной ошибке Telegram API webhook возвращает 503 для повтора, не выводя тело запроса или API URL.
Возможна повторная доставка сообщения при сетевой неопределённости; exactly-once для внешнего API не обещается.

Источник: [setWebhook, secret_token, совместимость с getUpdates](https://core.telegram.org/bots/api#setwebhook).

## 6. Запустить доставку уведомлений

Текстовые уведомления ставятся в очередь **database / notifications**. Аналитика сохраняет свой прежний backend;
Redis для Telegram jobs включать не нужно. Должны существовать стандартные таблицы Laravel jobs/failed_jobs.

Проверка накопившихся сообщений (команда завершится после опустошения очереди):

```bash
docker compose -f docker-compose.prod.yml exec app php artisan queue:work database --queue=notifications --stop-when-empty --tries=3 --timeout=45
```

Для постоянной работы нужен Supervisor/systemd либо отдельный корректно настроенный worker-контейнер:

```bash
docker compose -f docker-compose.prod.yml exec -T app php artisan queue:work database --queue=notifications --sleep=3 --tries=3 --timeout=45 --max-time=3600
```

Процесс должен автоматически перезапускаться после выхода/пересоздания app. Не полагаться на открытую SSH-сессию.
Entrypoint текущего app запускает PHP-FPM: простого изменения command у копии сервиса недостаточно для worker.
После выкладки кода/config перезапустить worker. Наблюдать за `php artisan queue:failed` и логом Laravel;
после исправления причины можно повторить конкретные failed jobs через `queue:retry ID`.

Job зашифрован APP_KEY, до 3 попыток, задержки 10/60 секунд. Ошибки постановки логируются и не блокируют вход.
Если worker не запущен, вход продолжит работать, а уведомления останутся в jobs. Не менять APP_KEY без плана
для уже зашифрованных задач. Фото/медиа через существующие методы отправляются синхронно с безопасным логированием;
новый ключевой бот медиа и обучение не раздаёт.

| Событие | Доставка во второй бот |
|---|---|
| Заявка на учётную запись `/about/request` | Существующее уведомление через очередь |
| Заявка на устройство | Уведомление без device_key |
| Неодобренное устройство | Существующий алерт без device_key |
| Успешный вход web / Filament / mobile | ФИО, ID, канал, IP и время |
| Ошибка учётных данных / неактивный аккаунт | До одного алерта на IP в минуту; аналитика продолжает писать все события |
| Попытка запрещённого скачивания документа | Алерт и прежний отказ 403 |
| Баг-репорты, Backstage | Существующие вызовы используют бот уведомлений |

Лога выхода в Telegram этот пакет не добавляет; существующая аналитика logout сохраняется.
Новые события аналитики: telegram.account_linked / telegram.account_unlinked; выдача ключа использует
telegram_key_requested с явным actor. Соль, ключ и сырой link token в эти события не включаются.

## 7. Если основной сервер не может обращаться к api.telegram.org

Использовать **два отдельных relay**, по одному на токен, либо сначала проверить доступность прямого HTTPS.
Исходники `telegram-relay/` обновлены: fail-closed secret, allowlist API-методов, без журналирования содержимого,
Dockerfile с PHP cURL, публикация только на loopback. Старый deploy скрипт с токеном больше не использовать.

На relay-сервере подготовить два отдельных каталога/Compose projects (`-p arm-tg-key` и `-p arm-tg-alerts`)
с файлами из telegram-relay. В каждом `.env` свой TELEGRAM_BOT_TOKEN и независимый случайный RELAY_SECRET,
разные RELAY_PORT (например 8088/8089). Установить права .env 600. `bash deploy-relay.sh` копирует пустой шаблон
при отсутствии .env и останавливается, пока настройки не заполнены.

Перед loopback-портами настроить HTTPS reverse proxy с действительными сертификатами и firewall; желательно
ограничить доступ IP основного сервера. ALLOWED_IPS в PHP проверяет REMOTE_ADDR: за локальным reverse proxy
это может быть адрес proxy, поэтому ограничение внешних IP лучше сделать в самом proxy/firewall.
Не доверять произвольному клиентскому X-Forwarded-For. Пустой ALLOWED_IPS не отменяет обязательный RELAY_SECRET.

В ARM:

```dotenv
TELEGRAM_KEY_RELAY_URL=https://key-relay.example/
TELEGRAM_KEY_RELAY_SECRET=СЕКРЕТ_РЕЛЕЯ_КЛЮЧЕЙ
TELEGRAM_RELAY_URL=https://alerts-relay.example/
TELEGRAM_RELAY_SECRET=ДРУГОЙ_СЕКРЕТ_РЕЛЕЯ_УВЕДОМЛЕНИЙ
```

Токены можно хранить только на соответствующих relay: configured() допускает HTTPS relay + secret без локального
bot_token. Но TELEGRAM_KEY_BOT_USERNAME и webhook secret всё равно нужны в ARM. Проверьте getMe обеих команд:
два relay не должны случайно использовать один токен. После изменения env пересоздать relay-контейнеры.
Relay не заменяет входящий webhook: Telegram всё равно должен иметь доступ к HTTPS-домену ARM.

## 8. Проверить пользовательский сценарий

1. Войти активным тестовым пользователем ARM. На барьере нажать «Получить ключ через Telegram».
2. Создать ссылку → открыть в своём Telegram → нажать «Запустить». Ввести /key, сравнить с прохождением барьера.
3. Проверить: чужой Telegram без привязки ключ не получает; ссылка одноразовая и через 10 минут истекает.
4. Отвязать Telegram на сайте, проверить отказ. Снова привязать и заблокировать пользователя в ARM — ключ недоступен.
5. Выполнить вход и тестовую заявку устройства, проверить административный чат и обработку очереди.
6. Проверить тестовую попытку скачивания: остаётся 403, приходит алерт. Содержимое ключа не должно попадать в админ-чат.
7. Проверить неверный webhook secret: 403. После успешных тестов отметить release SHA/дату в этом документе.

`protect_content` затрудняет пересылку сообщения, но не мешает человеку переписать общий ключ вручную.
Четыре значения 0–3 дают всего 256 комбинаций; существующие лимиты барьера остаются обязательными.
Факт прохождения барьера всё ещё хранится в сессии: отложенный этап 11 про месяц/устройство не реализован здесь.

## Откат

Перед откатом отключить webhook ключевого бота (`telegram:manage key --clear-webhook`), чтобы он не попал
в старый небезопасный обработчик. Вернуть согласованный release кода/assets, очистить кеш и перезапустить workers.
Аддитивные таблицы можно оставить до отдельного решения; не удалять привязки автоматически.
Старый раскрытый токен не восстанавливать. После восстановления нового release заново установить защищённый webhook.
