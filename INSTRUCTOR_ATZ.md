# Подстройки и учёт АТЗ

Реализовано локально 31.10.2026. Страница `/journal/training-requests`, пункт «Подстройки АТЗ» в инструкторском меню. Доступ только активному инструктору с назначенной колонной.

Карточка содержит месяц, тип смены (например А2), отдельное количество участников и список выбранных машинистов. Участники — действующие пользователи driver своей колонны; поиск по ФИО/табельному, выбранные фамилии выводятся отдельно. Количество должно совпадать с числом уникальных выбранных работников. Карточки можно редактировать и удалять.

Лимит 10 сохраняемых карточек на инструктора и календарный месяц. Удаление освобождает место; перенос в другой месяц проверяет его лимит. Лимит учитывает все карточки автора, даже после смены колонны; доступ к прежней колонне автоматически не выдаётся. При смене состава колонны перед сохранением необходимо актуализировать группу.

## Реализация

- InstructorTrainingRequests — отдельный сервис проверки состава, владения, лимита, версий и квитанций UUID. Повтор того же запроса возвращает сохранённый результат, другой запрос с тем же UUID получает 409. Устаревшая версия возвращает ошибку формы без перезаписи.
- TrainingRequestController — веб CRUD в routes/journal.php с существующими session/CSRF и middleware журнала. Для JSON-запросов те же маршруты возвращают JSON; это не опубликованный мобильный API.
- Три таблицы: instructor_training_requests, instructor_training_members, instructor_training_operations. Создание/редактирование/удаление и квитанция атомарны; блокировка User инструктора сериализует месячный лимит. Участники и профили проверяются под блокировками.
- Существующие индивидуальные Podstroika не изменены. Новых событий аналитики не добавлено, как предусмотрено согласованным планом.

## Миграция и выкладка

Новая миграция: `database/migrations/2026_10_31_100000_create_instructor_training_requests.php`. На production она ещё не применялась. Для выпуска сначала резервная копия и проверка статуса миграций; применять эту миграцию административным способом согласно SERVER_HARDENING_RUNBOOK.md. Не запускать все непроверенные миграции и не выдавать DDL runtime-пользователю. Код маршрутов и интерфейса переключать после создания таблиц, пересозданием контейнера по действующему runbook.

Первичный откат интерфейса — возврат кода при сохранении новых таблиц. Откат самой миграции удалит карточки и историю операций, поэтому не выполнять его после пользовательского ввода без сохранения данных. Production в рамках реализации не изменялся.

## Второй этап — учёт и периодичность (31.10.2026)

На той же странице добавлены «Отметить проведённое занятие», «Периодичность АТЗ» и таблица учёта по своей колонне. Инструктор явно выбирает фактическую дату (не в будущем), вид atz/atz_line и присутствовавших из состава карточки. Тип смены А2 не определяет вид норматива автоматически. Непришедшим выполнение не засчитывается.

Одна карточка подтверждается один раз. Повтор того же UUID возвращает прежнюю квитанцию; иной запрос тем же UUID — 409. После подтверждения нельзя удалить или переписать исходную карточку: история фиксирует дату, вид, смену, период на момент проведения, имена и табельные номера присутствовавших. Исправление подтверждённых занятий отдельным интерфейсом в этот этап не входит. Не редактировать такую историю прямым SQL для обычной работы.

Факт и участники хранятся в instructor_training_completions / instructor_training_attendance. Существующий journal_crew_normatives обновляется атомарно вместе с историей, карточкой и квитанцией. Новый вид нормативов не создавался. Поздно внесённое старое занятие сохраняется в истории, но не уменьшает last_date. Настройки atz_months/atz_line_months общие с прежним экраном, отдельно 1–24 месяца для двух видов. Изменение пересчитывает next_date от сохранённого последнего выполнения для принадлежащих инструктору записей текущей колонны, а не от сегодняшнего дня.

Календарь АТЗ использует addMonthsNoOverflow: 31.01.2026 + 1 месяц = 28.02.2026; 31.01.2024 + 1 месяц = 29.02.2024. Расчёты других видов КИП в этой задаче не менялись. Поля даты АТЗ в старой сетке нормативов доступны только для чтения; менять выполнение следует через учёт присутствия. Старое сохранение сетки сериализуется с учётом и не может переписать дату АТЗ. Старый экран настроек использует тот же пересчёт периодов.

Существующая уникальность журнала — (user_id,type). Если норматив уже закреплён за другим инструктором/колонной, подтверждение отклоняется целиком с объяснением, без захвата чужой записи. Переназначение исторических нормативов при переводах — отдельная административная процедура, автоматической миграции в этой задаче нет.

История отображается в карточках выбранного месяца планирования; фактическая дата может отличаться от месяца заявки. Текущие последние/следующие сроки и просрочки видны в таблице своей колонны и существующих представлениях нормативов. Новых событий аналитики не добавлено; факты занятий и квитанции сохраняются в PostgreSQL.

### Выпуск

Вторая миграция: database/migrations/2026_10_31_110000_create_instructor_training_completions.php, после 2026_10_31_100000. Обе пока только локально/в тестах, production не изменялся. Перед переключением кода нужны обе таблицы этапов и проверенные административные миграции по действующему runbook. При откате кода сохранять новые таблицы и факты: rollback второй миграции удаляет историю, а обратного пересчёта journal_crew_normatives автоматически не выполняет. Для реального отката данных потребуется согласованное восстановление, не один migrate:rollback.
