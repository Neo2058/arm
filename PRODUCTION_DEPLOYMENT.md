# Обновление production после усиления защиты

Сервер: `deploy@83.220.173.171`, проект: `/home/deploy/arm`. CI/CD пока нет.
Код доставляется через GitHub; `public/build` и APK игнорируются Git и передаются отдельно.
Изменения PHP видны контейнеру через bind mount: не выполняйте `git pull` до подготовки схемы и сборок.

## Подготовка на компьютере

1. Просмотреть `git status` и diff. Выделить файлы выпуска; не добавлять чужие заметки и секреты.
2. Выполнить относящиеся к изменениям тесты. Для веба собрать `npm run build`.
3. Если менялся мобильный код, собрать подписанный APK с прежним сертификатом и увеличенным `versionCode`. Проверить подпись, версию и SHA-256; сохранить метаданные выпуска. Публикация одного веб-кода не обновляет установленное приложение.
4. Закоммитить выбранные файлы и выполнить `git push origin main`. Записать точный SHA выпуска.
5. Передать сборки во временный каталог вне `public`, сверить SHA-256 после передачи.

## Подготовка сервера

Из `/home/deploy/arm` проверить состояние контейнеров и свободное место. Сохранить текущий SHA, изменённые на сервере файлы, прежние веб-ресурсы и APK.
Сделать свежую зашифрованную резервную копию по `FULL_BACKUP_2026-10-30.md`, проверить квитанцию восстановления и по возможности скачать копию на компьютер.
Затем `git fetch origin main`: fetch сам по себе работающий код не меняет.

Новые миграции просмотреть отдельно. Совместимые добавочные миграции доставить и применить до переключения кода, строго по выбранному пути:

```sh
cd /home/deploy/arm
sudo python3 scripts/arm-admin-artisan.py migrate:status
sudo python3 scripts/arm-admin-artisan.py migrate --force --path=database/migrations/ИМЯ_ПРОВЕРЕННОЙ_МИГРАЦИИ.php
```

Проверить доступ runtime-роли к новым таблицам. Она намеренно не имеет DDL-прав.
Несовместимые изменения схемы требуют отдельного плана и окна обслуживания.
Не запускать все накопившиеся миграции без просмотра.

## Переключение и проверка

После подготовки схемы переключить checkout на выбранный коммит через fast-forward, сохранив существующие серверные изменения. Не использовать `reset --hard` или `clean`.
Доставить новые файлы `public/build`, затем атомарно заменить `manifest.json`; старые файлы с хешами оставить для открытых страниц.

Команды выполнять из `/home/deploy/arm`, с действующим `COMPOSE_FILE` из серверного `.env`, без подмены его базовым compose-файлом:

```sh
sudo docker compose config --quiet
sudo docker compose up -d --no-deps --force-recreate --wait --wait-timeout 60 app
sudo docker exec arm-nginx nginx -t
sudo docker exec arm-nginx nginx -s reload
sudo python3 scripts/verify-readonly-runtime.py --container arm-app --url https://www.xn---15-7edz.xn--p1ai
```

Не выводить полный `docker compose config` в общие логи: он может содержать секреты.
Не выполнять `optimize:clear`, `config:clear`, `package:discover` или `vendor:publish` в обслуживающем read-only контейнере. Кеш готовится при его запуске.

Проверить HTTP, авторизацию, новые маршруты и отсутствие доступа без нужной роли. После готовности API атомарно заменить APK, сверить серверный SHA и скачивание через `/install/android`.
На телефоне установить обновление и проверить сценарий под реальным пользователем без создания фиктивных рабочих данных.

## Откат

При проблеме вернуть только затронутые исходники, прежний manifest и APK, пересоздать app и проверить HTTP. Сохранить новые пользовательские данные.
Не выполнять `migrate:rollback` автоматически: даже новые таблицы уже могут содержать данные.
Зафиксировать итог, SHA, место резервной копии и оставшиеся ручные проверки в документе выпуска.

Релиз АТЗ от 31.10.2026 использует проверенный разовый `scripts/deploy-atz-release.py` с собственными контрольными суммами и двумя точными миграциями. Он не является универсальным скриптом следующих релизов и не предназначен для повторного запуска.
