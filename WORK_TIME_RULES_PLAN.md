## Фактические параметры копии ARMNRD

| Поле NRDPAR | Значение | Смысл |
|---|---|---|
| NR_VECH1 / NR_VECH2 | 16.00 / 22.00 | Вечер 16:00–22:00 |
| NR_NOCH1 / NR_NOCH2 | 22.00 / 06.00 | Ночь 22:00–06:00 следующего дня |
| NR_12 | -+ | Первый знак не +: режим отдыха по формуле |
| NR_1VIH / NR_2VIH | 42 / 66 | Параметры выходных; в Laravel применяются напрямую в fixed-режиме |
| NR_MINV / NR_NOVIH | 3 / 12 | Интервал одиночных выходных / предел рабочих дней подряд |
| NR_KINT | 0 | Дополнительный контроль коротких интервалов отключён этой настройкой |
| NR_ONOCH | + | Включён специальный пересчёт связки ночь–с ночи |
| NR_NSM1 / NR_NSM2 | 3+ / 4+ | Ночные коды оригинала |

Это значения предоставленной копии программы, не проверка актуальных нормативных документов
и не утверждение о текущих настройках production. При реализации сначала сверить NaryadNorm.planir.
PLANIR Laravel дополнительно включает 5+ в ночные контроли: существующее ужесточение не ослаблять.

## Что уже есть в Laravel

`PlanirRulesService::requiredIntervalHours`:
- formula, без выходного: max(12 часов, 2 × продолжительность предыдущего дежурства);
- formula, n выходных: max(18 + 24n, 2 × продолжительность + 24n);
- fixed: настраиваемые 12 / 42 / 66 часов.

Это формулы существующего сервиса с его настройками, а не новые константы для каждого случая.
Связку ночной смены и продолжения учитывать через existing previousDutyHours;
проверять границы месяца и исключения. В PLANIR.PRG `r_interval` также есть удвоение
продолжительности и объединение ночь+с ночи. Применимость случаев сверять тестами, не копировать
только одну формулу в новый контроллер. Сервис также проверяет выходные и последовательности смен.

`AccountingImporter` уже переносит границы вечера/ночи и merge_night в planir.
`ShiftHoursService` берёт готовые часы из разбивки; это не универсальный расчёт пересечения
произвольных пользовательских интервалов с вечером/ночью.
`FoxTime`: 5.30 означает 05:30, не 5,3 десятичного часа.
`Payroll/ShiftCalculator` сейчас вычитает break_duration; для нового личного учёта это
противоречит подтверждённому правилу. Не менять старые записи/формулы без миграционного плана.

## Найденный специальный режим ночных

`UCHET.PRG`, c_ls (2368), rs_noch (3453), vse_noch (3512):
при NR_ONOCH=+ обрабатывается связка ночного кода NR_NSM1/NR_NSM2 и смены «1»
на следующий день у того же табельного. Если вычисленные ночные часы >= половины общей
продолжительности связки, обе части пересчитываются через vse_noch:
линейные часы и резерв становятся ночными, вечерние обнуляются, включая второго работника.
Не включать это правило безусловно для любой смены, пересекающей полночь.
В просмотренном Laravel-коде параметр импортируется/редактируется, но обработчик этого
пересчёта не найден. Перенос и эталонные примеры нужны до обещания совпадения ночных доплат.

## Результат следующего этапа: production и дополнительные алгоритмы

Владелец разрешил приступить к следующему этапу. Выполнено read-only чтение production НСИ;
база, настройки и расчётный код не менялись. Подробная спецификация:
`WORK_TIME_RULES_COMPARISON.md`.

Production использует formula, 12/42/66, интервал выходных 3 дня, максимум 12 дней,
короткий интервал 0, ночные коды 3+/4+/5+. Ключи evening_from/to, night_from/to,
merge_night отсутствуют в effective settings. Их отсутствие нельзя интерпретировать
как намеренно выключенное правило. Планировать явную инициализацию из проверенного NRDPAR
с сохранением существующих значений, без запуска полного импорта НСИ мимоходом.

Дополнительно найден CNTSMEN.PRG: при расчёте отдельной смены применяется порог >=50%
ночных часов и перевод всей смены в ночную (не только парный UCHET.rs_noch).
NR_ROUND=+ в исходном DBF означает округление sub_vr до 1 десятичного знака часа,
NR_ROUND=- — до 2. Импорт этого параметра в Laravel не найден.
Точные минуты и совместимые округлённые часы должны храниться/выводиться раздельно.
