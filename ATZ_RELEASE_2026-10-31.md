## Состав

Веб: карточки АТЗ, 10 на инструктора/месяц, выбор своей колонны, отдельное число участников, фактическая явка, история и периоды atz/atz_line. API и приложение используют те же InstructorTrainingRequests/InstructorTrainingAccounting, а не копии бизнес-правил.

Android: Журнал инструктора → Занятия АТЗ. Создание, редактирование, удаление карточек, выбор присутствовавших, дата/вид занятия, просмотр учтённых занятий и настройка обоих периодов. Последние/следующие сроки также доступны в «Бригада и нормативы». Сетевой клиент arm-nrd остаётся работой владельца.

GET /api/mobile/journal/training-requests?month=YYYY-MM; GET /crew с пагинацией по 50. POST базового пути, PATCH/DELETE /{id}, POST /{id}/complete, POST /periods. Все пути находятся под Sanctum и EnsureActiveApiUser; сервис повторно проверяет instructor/активность, владельца и колонну. Ответы private/no-store. Обычный пользователь не получает доступ к инструкторскому API.

На Android отдельный приватный namespace training-requests, привязанный к API URL и ID пользователя. Черновик и точный запрос/UUID сохраняются до HTTP. Повтор вручную после неопределённого ответа сохраняет тело; выход из аккаунта очищает данные, повторный вход сохраняет. После 422 можно исправить отклонённую форму; 409 не приводит к скрытой подмене UUID. Новых нативных зависимостей нет.

## Порядок ручного обновления production

1. Изменения пока в локальной рабочей копии. Сначала просмотреть git diff/status, закоммитить и отправить именно файлы АТЗ. Не добавлять посторонний пользовательский TwoSideApi.md автоматически. Установщик и public/build игнорируются Git и передаются отдельно. Обычный git pull сам по себе APK не доставит.
2. До обновления сохранить код и старый установщик, сделать и проверить свежую резервную копию по FULL_BACKUP_2026-10-30.md. На production остаются пользовательские изменения Filament assets, bootstrap/cache/.gitignore и дополнительные файлы; не выполнять reset --hard/clean и не затирать их.
3. Получить исходники. Две новые миграции должны быть доступны текущему контейнеру до переключения нового кода, использующего таблицы. При поэтапной выкладке сначала доставить только миграции; не допускать запросов к новой странице до создания таблиц. При обычном обновлении checkout использовать окно обслуживания/контролируемое переключение, чтобы код и схема не расходились.
4. Из /home/deploy/arm выполнить проверенные миграции административным wrapper, строго по одной:

```sh
sudo python3 scripts/arm-admin-artisan.py migrate:status
sudo python3 scripts/arm-admin-artisan.py migrate --force --path=database/migrations/2026_10_31_100000_create_instructor_training_requests.php
sudo python3 scripts/arm-admin-artisan.py migrate --force --path=database/migrations/2026_10_31_110000_create_instructor_training_completions.php
sudo python3 scripts/arm-admin-artisan.py migrate:status
```

Не менять runtime DB credentials и не применять другие непросмотренные миграции. Default privileges административного владельца должны дать arm_runtime DML на новые таблицы/sequences; проверить чтение через runtime после миграций.

5. Передать собранный public/build вместе с manifest.json. Пересоздать app с действующим COMPOSE_FILE, включающим security и readonly overlays, по SERVER_HARDENING_RUNBOOK.md. Не запускать только базовый prod compose и не выполнять optimize:clear/config:clear в обслуживающем контейнере.

```sh
sudo docker compose config --quiet
sudo docker compose up -d --no-deps --wait --wait-timeout 60 app
sudo docker exec arm-nginx nginx -t
sudo docker exec arm-nginx nginx -s reload
sudo python3 scripts/verify-readonly-runtime.py --container arm-app --url https://www.xn---15-7edz.xn--p1ai
```

6. Проверить веб под инструктором и закрытость API без токена. GET API с Accept: application/json без токена должен вернуть 401, а не данные. Проверить свои/чужие колонны, сохранение и учёт в вебе; не отмечать реальное выполнение ради smoke-теста.
7. Только после готовности API разместить APK и его release-JSON. Сохранить прежний APK вне public и выполнить атомарную замену новым файлом с проверкой SHA-256. Предпочтителен существующий проверяющий publisher при доступных Android build-tools/Java; либо предварительно проверенный локально файл переносится под временным именем, сверяется sha256sum и переименовывается. Не публиковать неподписанный или заново подписанный другим ключом APK.
8. Установить обновление на реальный Android, войти инструктором и проверить общие веб/мобильные данные. Остальные пользователи не должны увидеть инструкторские формы.

## Откат

Сохранять новые таблицы и историю занятий. Возврат исходников/ресурсов к резервной версии и пересоздание app предпочтительнее разрушительного rollback миграций. Откат второй миграции удаляет историю и не восстанавливает прежние даты нормативов. Пользователи с code15 не смогут обновиться обратно на code14 обычной установкой: при проблеме мобильного клиента нужен исправленный APK с code16 или выше. Старый APK сохраняется для диагностики, но не является бесшовным downgrade.
