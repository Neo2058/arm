## Сценарий

Профиль → «Формуляр · записи и проверка». Машинист видит активные задания администратора, вводит текст, отправляет на проверку. Инструктор также может вести собственные записи, но не проверять их; контроль колонны охватывает активных пользователей с ролью машиниста. Пустая колонна не открывает доступ ко всем сотрудникам.

На проверке → подтверждено либо возвращено с обязательным замечанием. Исправление возвращённой записи создаёт новую версию и сбрасывает текущую проверку. До возврата повторное редактирование запрещено. Существующие записи после миграции считаются ожидающими проверки, а не автоматически подтверждёнными. Проверка инструктором не является квалифицированной электронной подписью.

Статистика — матрица активных заданий и активных машинистов своей колонны. Есть статусы «Не внесено», «На проверке», «Подтверждено», «Возвращено», фильтры сотрудника/задания/статуса и страницы по 25 строк. Счётчики учитывают фильтры сотрудника/задания; фильтр статуса ограничивает список, оставляя общие счётчики по всем статусам. Это не статистика подписания инструктажей.

Веб: `/formular`, проверка `/formular?review=1`; ссылка доступна из обучения/росписей. Каноническая карусель не меняется. Прежний POST `/rosisi/log-formular/{task}` использует ту же проверку версий и не перезаписывает подтверждённые записи. Старый список формуляра в `/rosisi/statistics` для инструктора ограничен своей колонной; росписи документов этим этапом не меняются.

## API и сохранение

- `GET /api/mobile/formular` — собственные активные задания и записи.
- `GET /api/mobile/formular/review` — контроль колонны, фильтры `user_id`, `task_id`, `status`, `page`.
- `POST /api/mobile/formular/tasks/{task}` — `operation_id` UUID, `version` (0 при отсутствии записи), `entry_text` до 10 000 символов.
- `POST /api/mobile/formular/logs/{log}/review` — UUID, версия, `decision=confirmed|returned`, `review_comment` до 2000 символов, обязателен для возврата.

Требуются актуальная активная учётная запись и подходящая роль. Monitor-токены запрещены. GET-ответы без кеширования, мутации ограничены 20/min. ID автора определяется сервером. Квитанция операции и новая версия фиксируются одной транзакцией; повтор UUID с тем же телом возвращает прежний результат, с другим — 409. Конфликт версии также 409. Последовательные запросы автора сериализуются блокировкой строки пользователя, изменения записи — её row lock; это не заменяет будущий многопроцессный нагрузочный тест PostgreSQL.

Локальный черновик и точное тело запроса сохраняются в private FileSystem, namespace `formular`, отдельный scope API URL + user ID. Автоматических повторов нет. При неопределённом сетевом результате разрешён только повтор прежнего UUID/тела. После явного отказа можно снять запрос и сохранить текст; после 409 необходимо сравнить актуальную запись и открыть её новую версию. Перевход сохраняет черновик; явный выход удаляет scope и блокирует поздние записи старой сессии. Это локальное хранение приложения, отдельного шифрования пользовательским устройством данный этап не вводит.

`formular_operations` сохраняет результаты операций, включая текст и предыдущие результаты проверки. Отдельного интерфейса полной истории редакций и политики очистки квитанций пока нет; не удалять их автоматически. Основная запись по-прежнему одна на пару сотрудник/задание.

Аудит после commit: существующее `formular_logged` (resource_id задания) и два согласованных события проверки. Только ID записи/машиниста/проверяющего, без текста и замечаний. Операционные данные — PostgreSQL; схема ClickHouse не меняется. MinIO не используется и не меняется.

## Приёмка

Два устройства одного машиниста: отправка, повтор после потери ответа, запрет дубля/перезаписи; инструктор другой колонны/машинист/monitor не видят контроль; инструктор своей колонны возвращает запись, машинист исправляет, инструктор подтверждает. Старый открытый экран не должен подтвердить изменённую версию. Проверить отсутствие записи в статистике «Подтверждено» до реальной проверки. Отдельно проверить веб → APK и APK → веб, смену аккаунта, явный выход и перевход после 401.

Перед инструкторской приёмкой: на production у двух активных инструкторов нет колонны. Администратору назначить достоверное «№ Колонны» в профиле; без этого проверка намеренно недоступна (422).
