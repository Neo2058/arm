# Редакции документов и вывод из действия

12.11.2026. Код подготовлен локально, **не опубликован**. Production и опубликованный APK остаются 1.1.9. [Общий план](../roadmap/DOCUMENT_CATALOG_PLAN.md).

## Как пользоваться после внедрения

1. В админке открыть действующий документ и нажать **«Новая редакция»**. Форма копирует название, размещение, роли и папку росписей. Нужно загрузить другой оригинал, указать обозначение редакции, дату введения и основание замены.
2. Явно подтвердить вывод предыдущей редакции и необходимость проверки тестов/ссылок. До успешного сохранения прежний документ действует. В одной транзакции старый выводится из действия, новый получает собственный document_id и становится действующим.
3. **«Вывести из действия»** позволяет отменить документ без замены. Требуются основание и подтверждение. Дата, автор и первое основание сохраняются; повтор запроса их не переписывает.
4. **«История редакций»** открывает всё семейство. Список админки по умолчанию показывает действующие документы; фильтры «Архив»/«Все» доступны явно. Архивная карточка только для чтения. При необходимости после отдельной отмены можно выпустить новую редакцию от последней в цепочке.

Оригиналы при этих действиях **не удаляются**. Удаление файлов — отдельный ещё не реализованный этап после проверки зависимостей. Срок хранения по возрасту и автоматическая очистка отсутствуют. Удаление карточек и непустых папок росписей через модели блокируется, чтобы не потерять историю каскадом.

## Что увидят сотрудники

Веб и APK показывают только действующие редакции. Старая исчезает из каталога и списка росписей. Каждая новая редакция требует собственного подтверждения ознакомления; старые даты остаются у прежнего ID, автоматически не обнуляются и не переносятся. Обозначение редакции отображается в обновлённых клиентах; старый APK игнорирует новое поле, но работает с новым ID и статусом корректно.

Доступ к выведенной редакции по обычному веб-пути для сотрудника и по мобильной signed URL прекращается сразу, даже если подпись URL ещё действительна. Администратор может открыть сохранённый оригинал через защищённый веб-маршрут с сессией. Уже полученные на устройство байты технически отозвать невозможно.

Тест старой редакции больше не запускается/не принимается к оценке. Его результаты и вопросы сохраняются в БД; собственная история результатов остаётся историей, не ссылкой на выполнение старого теста. Quiz и QuestionReference автоматически к новому ID не перепривязываются: номера страниц и смысл ссылок могли измениться. Ссылки на выведенный документ исключаются из плееров других тестов до проверки администратором.

## Устройство и ограничения

`documents.root_document_id` объединяет цепочку, `replaces_document_id` уникален для непосредственного предшественника. У исходной карточки root=NULL, а её ID является ID семейства. Добавлены порядковый номер/обозначение редакции, effective_on, withdrawn_at/by/reason. Частичный уникальный expression index PostgreSQL/SQLite на COALESCE(root_document_id,id) запрещает две невыведенные редакции одного семейства. Существующие строки остаются действующими, редакция «1», без массового переписывания ID и отметок.

`DocumentRevisions` требует действующего администратора или super_admin текущей сессии, перечитывает роль, сериализует публикацию и вывод PostgreSQL advisory lock тем же ключом, что проверка дублей. Повторная публикация от уже заменённого предшественника отклоняется; ошибки откатывают и новую карточку, и вывод старой. Для нового файла сохраняются проверка SHA-256 и уникальное имя объекта. Изменение file_path у существующей модели запрещено.

Публикация применяется сейчас, дата введения — сегодня или прошедшая дата. Планировщика будущего переключения нет; будущая дата отклоняется, чтобы не оставить промежуток без действующего документа. Автоматического восстановления отменённой редакции также нет.

Это история обычных подтверждений ознакомления, а не квалифицированная электронная подпись. SHA-256 используется для проверки файлов и дублей. Для старых ранее подписанных документов хеш вычисляется при индексации; он не доказывает, какие байты находились в хранилище в прошлом.

## Аудит

Переиспользуются одобренные `document.catalog_saved` и `document_folder.saved`. В событии только ID ресурса и имена изменённых полей; нет основания вывода, названия и пути. После commit. Общий AdminPanelAudit пропускает Document, чтобы не создать дубликат admin.document.* с названием. Остальные ресурсы сохраняют прежний аудит.

## Подготовка выпуска

Перед включением кода применить проверенные миграции `2026_11_12_160000_add_document_folders.php` и `2026_11_12_170000_add_document_revisions.php` административной ролью. Для первой таблицы нужны DML/sequence permissions runtime-роли. Не запускать все накопившиеся миграции автоматически. Процесс выкладки должен обеспечить наличие схемы до обслуживания нового кода; прежний PHP не умеет учитывать архив.

После начала эксплуатации редакций нельзя просто откатить исходники на прежнюю версию: она снова покажет архивные документы и разрешит старые ссылки. Нужен forward-fix либо отдельно проверенный откат, сохраняющий ограничения withdrawn_at. Автоматический migrate:rollback не допускается.

Перед выпуском: резервная копия/проверка восстановления, PostgreSQL-проверка схемы и конкурентных операций, индексация SHA-256, штатная read-only выкладка, новый APK с увеличенным versionCode/прежней подписью и проверкой установки. Физические production-файлы для проверки не выводить из действия и не удалять.

## Результаты проверок

121 PHP-тест / 629 assertions: редакции, формы Filament, архивные фильтры, защита Locked-поля источника, роли, отмена по старым ссылкам, сохранение росписей/результатов, откат неудачной публикации, обязательные проверки журнала/файлов/планирования/маршрутов и общий аудит. 2 Node-теста дерева/поиска, Vite build и Android JS export прошли. Нативный APK этого этапа не собирался; физическая приёмка и production-выпуск не выполнены.

На одноразовом **локальном PostgreSQL 17** применены все миграции и прошли три конкурентные проверки: две публикации от одного источника → одна редакция; два одинаковых файла → одна карточка; вывод из действия одновременно с росписью → согласованный результат без подписи после вывода. Это не нагрузочный тест production. Запуск из корня: `python3 tests/Support/run-document-revisions-pg.py` (PostgreSQL CLI в PATH, PHP pdo_pgsql/pcntl). Скрипт создаёт закрытый временный Unix-сокет без TCP, использует искусственные записи и удаляет свой кластер после остановки. Сам PHP helper дополнительно проверяет префиксы host/database и APP_ENV=testing. Рабочие базы, внешние сообщения и MinIO не используются.
