# ARM: закрытый мониторинг сервера и приложения

Применено **06.11.2026**. Самостоятельный Compose-проект `arm-monitoring`, отдельно от приложения. Grafana 13.3.0 и Prometheus 3.16.0; при установке образы закреплены по RepoDigest в серверном `/etc/arm-monitoring/images.env`.

## Открыть панель

На компьютере владельца подготовлен SSH-туннель. Открыть:

**http://localhost:3000/d/arm-operations**

Логин: `arm-admin`. Пароль сохранён только в приватном файле компьютера `~/.tch15-arm/monitoring-credentials.txt` с правами 0600. Не копировать его в чат, Git или презентацию. Серверный экземпляр пароля — `/etc/arm-monitoring/grafana-admin-password`, root:472, 0440.

Если туннель закрыт, в терминале компьютера:

```sh
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:3000:127.0.0.1:3000 deploy@83.220.173.171
```

Оставить терминал открытым; Ctrl+C закрывает этот туннель. Если локальный порт уже занят, сначала проверить существующий туннель. Подключение, открытое ассистентом, временное и может завершиться вместе с сессией/сетью компьютера. Для самостоятельной работы использовать команду выше в своём терминале. Остановка туннеля не останавливает сбор метрик на сервере.

Анонимный вход и самостоятельная регистрация Grafana отключены. Панель предназначена администратору, не всем пользователям ARM. Пароль администратора не передавать пользователям ресурса.

## Что измеряется

Дашборд **«ARM — сервер и приложение»**, 28 блоков:

- CPU, RAM, SWAP, свободный диск, нагрузка, сеть и дисковые операции хоста.
- Состояние, здоровье, перезапуски, CPU и относительная память восьми рабочих контейнеров.
- Локальная HTTPS-проверка страницы входа, её длительность и HTTP-статус.
- Скорость журналируемых HTTP-запросов, ошибки 5xx и p95 времени ответа.
- Число соединений БД и видимые runtime-роли активные запросы дольше 5 секунд.
- Количество PHP-FPM worker-процессов: это **не** число занятых workers или длина очереди FPM.
- Ожидающие/неуспешные задания БД и возраст старейшего задания; сюда попадают уведомления. Это **не** измерение отложенной аналитики с `QUEUE_CONNECTION=deferred`.
- Возраст последнего серверного recovery-набора с квитанцией PASS, свежесть сборщика и состояние компонентов мониторинга.

Сборщик запускается раз в 30 секунд, Prometheus читает показатели каждые 15 секунд, панель обновляется раз в 15 секунд. Поэтому это оперативный мониторинг, а не мгновенное наблюдение каждого события. Для графиков скорости и p95 требуется накопление данных.

HTTP-метрики относятся к запросам, для которых Nginx пишет access log. Статика и маршруты с `access_log off` не включены. Есть отдельная строка только с `$msec`, `$status`, `$request_time`, без IP/URI/query/token; существующие access logs не удалены. Внутренние проверки страницы входа тоже входят в счётчики. Читаются не более 5000 последних строк за цикл; при достижении лимита появляется показатель неполноты. При высокой нагрузке нужен пересмотр способа доставки метрик и ротации журналов.

История Prometheus ограничена 30 днями или 2 ГБ блоков — что наступит раньше. WAL и служебные файлы могут занимать дополнительное место: это не файловая квота. Собственные Docker-логи двух новых сервисов ограничены 2 × 5 МиБ для каждого. Политика журналов действующего Nginx этим не заменяется.

## Уведомления

Используется существующий Telegram-канал алертов, через отдельную root-only копию только настроек транспорта. Уведомления не зависят от Laravel или его очереди и не содержат персональные данные. После отдельного разрешения владельца отправлено **одно тестовое сообщение**, ответ API подтвердил доставку.

При ротации бота или смене relay требуется отдельно синхронизировать `/etc/arm-monitoring/notifications.json` административно: это снимок настроек, а не автоматически обновляемая ссылка на конфигурацию Laravel. Значения не передавать через аргументы процесса или общие логи.

Сигнал отправляется при устойчивой проблеме, повтор — не чаще одного раза в 6 часов; при восстановлении формируется отдельное сообщение. Условия:

- CPU >85%, доступная RAM <10%, свободный диск <15%.
- Рабочий контейнер недоступен/нездоров, веб-вход не отвечает HTTP 200 либо проверка занимает >3 секунд.
- Появление неуспешных заданий, ожидание задания БД >5 минут, соединения >80% лимита, видимый запрос >5 секунд.
- Более 5% ошибок 5xx при не менее 10 учтённых запросах за цикл.
- Недоступность Grafana, Prometheus или HTTP-экспортера.
- Серверная копия старше 72 часов либо не найдена.

Обычный период подтверждения — 2 минуты, для старой копии — 10 минут. Таймаут проверки локальных компонентов — 3 секунды. При аварийном завершении сборщика отдельный systemd OnFailure отправляет сигнал, с ограничением запусков обработчика. Отказы доставки не удаляют проблему из состояния; повтор выполняется следующим циклом, без вывода токенов.

Prometheus дополнительно показывает правила устаревания сборщика и недоступности экспортера. Доставка Telegram реализована root-owned сборщиком/OnFailure, отдельный Alertmanager не установлен. Отключение самого таймера, всего Docker, сервера, сети или канала доставки требует независимого внешнего наблюдателя — текущий мониторинг на этом же хосте не гарантирует такой сигнал. Пороги являются начальными настройками и требуют оценки после накопления пользовательской нагрузки.

Никаких автоматических блокировок, шифрования/удаления файлов, повторного исполнения failed jobs или очистки рабочих данных нет.

## Изоляция и ресурсы

- Только `127.0.0.1:3000` (Grafana), `127.0.0.1:9090` (Prometheus), `127.0.0.1:9108` (текстовые метрики). Публичные порты, firewall и SSH не менялись.
- Контейнеры мониторинга не получают Docker socket, корневую файловую систему хоста, окружение ARM, административные доступы БД или Telegram-токены.
- Grafana: максимум 384 МиБ, 0.5 CPU; Prometheus: 512 МиБ, 0.5 CPU. Read-only rootfs, непривилегированные UID, cap_drop ALL, no-new-privileges, ограничения процессов и tmpfs.
- Используется host network для доступа к loopback, но сервисы привязаны только к loopback. Это не полная сетевая песочница: серверные плагины/административные возможности Grafana требуют доверенного администратора.
- Отдельный root-owned сборщик читает фиксированный список команд Docker и агрегаты через runtime-подключение приложения. Его код установлен в `/usr/local/libexec/arm-monitoring`, не исполняется из deploy-owned checkout по расписанию.
- systemd ограничивает сборщик: CPUQuota 35%, MemoryMax 256 МиБ, Nice 10, ProtectSystem, NoNewPrivileges; запись только в каталоги собственных метрик и состояния. HTTP-сервис работает от nobody и читает только подготовленный текст метрик.
- `/etc/arm-monitoring/notifications.json` — 0600, не примонтирован в Grafana/Prometheus. Приватное состояние — `/var/lib/arm-monitoring/private`, 0700. В Git только шаблоны без значений секретов.

## Проверка установки

06.11.2026 подтверждено:

- Grafana: успешный браузерный вход, дашборд из 28 блоков и чтение данных через datasource.
- Обе Prometheus targets — up; все четыре этапа сборщика — up; сбор около 4 секунд на текущей нагрузке.
- Loopback-привязка трёх портов, ограничения памяти/capabilities, отсутствие Docker socket в новых контейнерах.
- Read-only rootfs и `/var/www` приложения сохранены; приложение не пересоздавалось. Nginx прошёл `nginx -t` и reload; веб-вход продолжил отвечать 200.
- 6 локальных тестов: границы интервалов без дублей, histogram/status, игнорирование посторонних/дополненных строк, CPU, запрет перенаправления уведомлений, отсутствие пользовательских SQL-данных. PHP-фрагмент проверен синтаксически.
- Тестовое Telegram-сообщение доставлено после отдельного подтверждения владельца.

Во время настройки исправлены два дефекта мониторинга: закрытые права нового родительского каталога libexec и отсутствие PID в `docker top`. Таймаут самопроверки Grafana увеличен с 1 до 3 секунд. Они не потребовали пересоздания приложения; итоговая проверка всех источников прошла после исправлений.

На момент проверки: **0 ожидающих заданий, 21 запись failed_jobs**, последняя найденная серверная копия — **31.10.2026**. Записи не удалялись и задания не перезапускались. История failed_jobs требует отдельного разбора без публикации payload/секретов. Возраст серверной копии не подтверждает получение или свежесть копии на ПК. Автоматическое резервирование этой установкой не включено.

## Эксплуатация и остановка

```sh
sudo systemctl status arm-metrics-collector.timer arm-metrics-http.service
sudo systemctl show arm-metrics-collector.service -p Result -p ExecMainStatus
sudo docker compose --project-directory /etc/arm-monitoring --env-file /etc/arm-monitoring/images.env -f /etc/arm-monitoring/compose.yml ps
```

Не выводить полный Compose config/окружение. Проверка только синтаксиса — `config --quiet`. Метрики не помещать в общедоступный веб-каталог приложения.

Остановка только нового мониторинга:

```sh
sudo systemctl disable --now arm-metrics-collector.timer arm-metrics-http.service
sudo systemctl stop arm-metrics-collector.service
sudo docker compose --project-directory /etc/arm-monitoring --env-file /etc/arm-monitoring/images.env -f /etc/arm-monitoring/compose.yml stop
```

Данные и секреты не удаляются. Для полного отката агрегированного access log сначала сравнить текущий Nginx с сохранённым `nginx-before.conf` в `/root/arm-monitoring-install-*`. Возвращать файл только после проверки последующих изменений, затем `nginx -t` и reload. Не применять `docker compose down` к основному приложению.

Установщик `ops/monitoring/install.py` — только первая ручная установка: отказывается при существующем `/etc/arm-monitoring`. Не запускать повторно для обновления. Обновлять reviewed root-owned файлы, с отдельной проверкой конфигурации и откатом. При первоначальной установке мониторинга параметры доступа к БД/ролям, схема ClickHouse, события пользовательской аналитики и APK не менялись. Мобильное дополнение описано ниже.

## Мобильная панель (добавление 06.11.2026)

План и контроль выпуска: `docs/roadmap/MONITOR_MOBILE_PLAN.md`. Отдельный APK `ru.tch15.arm.monitor` читает агрегаты через `/api/monitor/snapshot`. Доступ — все активные `super_admin`, отдельный токен только для чтения на 12 часов. Скачивание — из профиля основного APK 1.1.1/code17, сервер проверяет обычный мобильный токен и актуальную роль. Установщик хранится в root-owned `/var/lib/arm-monitoring/installers/tch15-monitor.apk` (0444), доступен приложению через readonly `/run/arm-installers`; публичной ссылки нет. Пароли Grafana и SSH на телефон не передаются, loopback-порты остаются закрытыми.

После переключения вариантов Expo всегда проверять package ID, versionCode и сертификат фактического APK. `EXPO_PUBLIC_MONITOR_APP=1` нужен и при prebuild, и при Gradle; без флага собирается основной APK. Приватная подпись подставляется `mobile/plugins/with-release-signing.cjs` из файла владельца вне Git. События login/logout/выдачи установщика добавлены по отдельному согласию владельца, показатели в ClickHouse не записываются.
