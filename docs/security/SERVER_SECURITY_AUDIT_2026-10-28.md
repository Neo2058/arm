## Ограничения доказательств

Доступ deploy не даёт sudo без пароля. Не прочитаны live nftables/iptables,
полные auth/FPM/панельные логи и root-crontab. Сохранённые UFW-правила — не доказательство
фактически загруженного набора. Внешний TCP connect показал успех даже для портов,
не слушающих на хосте; последующие Redis PING, PostgreSQL SSLRequest и HTTP HEAD
не получили протокольного ответа. Такая точка измерения не позволяет надёжно
объявить БД публичной или порт панели доступным. Нужна независимая внешняя проверка
и сопоставление с live firewall IPv4/IPv6/Docker forwarding.

Roundcube include ссылается на PHP 7.4; host nginx конфигурация включает vhosts-includes.
Текущий основной HTTP/HTTPS обслуживает Docker Nginx; полная достижимость Roundcube
через ISPmanager/другие vhosts ещё не установлена. Не считать его доказанно публичным.
PHP 5.6.40 и 8.4.20 установлены в /opt, отдельных master этих конфигураций не найдено.
Наличие backport для старых сборок нужно выяснить у поставщика.

Ночных внешних неизменяемых backups и тестового восстановления в этой проверке
не подтверждено. В доступных timers только dpkg-db-backup, что не является backup
ARM; ручные release-backups находятся на том же хосте. Это не доказывает отсутствие
root/provider backup. Аудит не даёт заключения об отсутствии компрометации.

## План исправлений: небольшие пакеты с отдельной приёмкой

### 1. Граница хоста и старые службы

- Получить административный отчёт о live firewall, ошибке Fail2Ban, root backup
  jobs и полном списке FPM/pool/vhost, не передавая пароли в чат.
- Выяснить использование почты/Roundcube/FTP/DNS/ISPmanager. Перевести нужное на
  исправленный runtime с проверкой совместимости; отключить ненужные службы.
- Ограничить панель VPN или согласованными IP; IPv4 и IPv6. Сохранить действующий
  SSH-сеанс и консоль провайдера, сначала проверить второй доступ, затем применять.
- Восстановить Fail2Ban по причине ошибки; проверить реальную блокировку и снятие
  на контролируемом тестовом IP. Не блокировать адреса доверенного proxy/администратора.

### 2. Базы и секреты

- Создать отдельную runtime-роль PostgreSQL: без SUPERUSER, CREATEDB, CREATEROLE,
  REPLICATION/BYPASSRLS; дать только необходимые права на текущую схему/таблицы/
  sequences и default privileges будущих миграций. Отдельная роль для миграций и backup.
  Проверить владельцев объектов, расширения и пользовательские права до переключения.
- Создать MinIO service account с политикой только для нужных bucket/actions.
  Административные ключи убрать из приложения; отдельно проверить uploads, streaming,
  удаление и необходимые Filament операции без изменения их логики.
- Заменить общий env_file явным набором переменных каждого сервиса. Ненужные
  APP_KEY/Telegram/DB ключи не должны присутствовать в MinIO/Postgres/поиске/аналитике.
- Nginx монтировать только public, нужные public-storage assets и TLS; не весь checkout.
  Раздельная edge↔app и app↔data сеть. Код app сделать read-only, разрешить запись
  только storage и требуемым cache-каталогам. Учесть migrations/build/deploy и entrypoint.
- Проверить no-new-privileges, capabilities и read-only rootfs на стенде, затем выкладка.
- Ротацию секретов планировать с учётом зависимостей; APP_KEY не менять вслепую:
  зашифрованные значения и сессии могут стать недоступны. При признаках утечки —
  процедура инцидента, отзыв токенов и восстановление с чистого окружения.

Приёмка: вход web/APK, CRUD смен/периодов, файл-прокси, Filament upload, Telegram,
очереди/ClickHouse, поиск; попытки доступа чужого сервиса к ненужным данным запрещены.
Обязательные feature-тесты доступа/файлов/маршрутов запускаются после правок.

### 3. Сохранность резервных копий

- Отдельное хранилище/аккаунт с версионированием и Object Lock/immutability.
  У рабочего сервера нет полномочий удаления/снятия retention.
- Backup PostgreSQL, MinIO, нужных app-storage и конфигурации; шифрование с ключом
  восстановления вне production. Секреты backup не передавать runtime приложения.
- Согласовать RPO/RTO; для малого RPO рассмотреть WAL/PITR, а не только ночной dump.
- Проверять свежесть, целостность и периодическое восстановление в изолированном
  окружении. Локальная копия не защищает от захвата root или уничтожения диска.

### 4. Мониторинг и реакция

Предложение для одного production-хоста: Wazuh-agent на сервере, manager/indexer
на отдельном узле; контроль целостности и системных событий, внешняя доставка логов.
Falco — дополнительный вариант для syscall/container detection, если нужна более
детальная видимость процессов; не ставить обе системы сразу без оценки нагрузки.
Grafana + Prometheus + Loki полезны для метрик/логов/доступности, но сами не обеспечивают
запрет выполнения кода или гарантированное сдерживание атак. Панели доступны через VPN,
exporters и Docker socket не открывать в интернет. Из 8 ГБ RAM примерно 4.6 ГБ available
на момент проверки; полный security/indexing stack лучше не размещать рядом с БД.

Первый этап — только наблюдение и настройка исключений:
- необычные дочерние процессы FPM, загруженные/запущенные бинарники;
- изменение кода, конфигурации, authorized_keys, cron/systemd, отключение защиты;
- новые пользователи/ключи/администраторы, контейнеры и изменения mounts/capabilities;
- подозрительный исходящий трафик, падения PHP, массовые ошибки входа и скачивания;
- рост DB-привилегий/DDL, backup age, heartbeat самого агента и прекращение доставки.

ARM законно запускает python3/extract_shifts.py, конвертеры, сканер файлов и
служебные команды. Правило «любая shell/Python = взлом» остановит штатную работу.
Нужен профиль разрешённых parent/child, paths, пользователей и deployment windows.
Логи минимизировать: без Authorization/cookies/паролей/полных signed URL и секретов.
Уведомления можно направить существующему Telegram-боту после настройки защищённого
канала отправки; в рамках аудита сообщения не отправлялись. Изменения событий
ClickHouse требуют отдельного согласования; инфраструктурные события туда не переносить.

Вторая стадия — ограниченная автоматическая реакция после проверки ложных срабатываний:
- подбор/сканирование: временная блокировка подтверждённого IP с TTL, allowlist и rollback;
- сильный сигнал RCE: оповещение, сохранение внешних логов и метаданных, изоляция
  затронутого контейнера от входящего/исходящего трафика и БД по заранее проверенному
  runbook; не выключать всё по одному слабому сигналу и не терять доступ администратора;
- подтверждённый root-компромисс: изоляция на стороне провайдера/внешнего firewall,
  отзыв ключей с чистого устройства, пересоздание сервера, проверенное восстановление.

Не использовать автоматические chmod/chattr/шифрование файлов как основной ответ:
они не отзывают прочитанные ключи, открытые соединения и данные в памяти; root может
снять локальные ограничения и отключить агент. Read-only код и минимальные права
нужны ДО инцидента, внешние логи и независимые backups — чтобы пережить захват хоста.
