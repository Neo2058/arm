# План развития: безопасный CI/CD ARM

Записан: 02.11.2026 по поручению владельца. Статус: **запланировано, не внедрено**.
Порядок: сначала CI без доступа к production, затем управляемая публикация после подтверждения владельца.
До внедрения действует [ручной порядок публикации](../operations/PRODUCTION_DEPLOYMENT.md).

## Этап 1 — автоматические проверки без доступа к серверу

- [ ] Настроить GitHub Actions на push и pull request, на временных GitHub-hosted runners.
- [ ] Выполнять PHP- и мобильные тесты, проверку зависимостей и сборку веба по lock-файлам.
- [ ] Использовать временные тестовые базы и тестовые секреты; не подключаться к production.
- [ ] Зафиксировать и разобрать существующие ошибки полного набора тестов учёта ЛС. Не скрывать их массовым исключением тестов и не обозначать полный набор как успешный.
- [ ] Выделить обязательные успешные проверки перед выпуском и настроить защиту основной ветки с учётом доступности функций тарифа.

Готовность: проверки воспроизводимы, ошибки блокируют соответствующий выпуск, CI не имеет производственных секретов или доступа к серверу.

## Этап 2 — проверяемые артефакты выпуска

- [ ] Собирать веб-артефакты из конкретного commit SHA; сохранять версию, контрольные суммы и результаты проверок.
- [ ] На сервер доставлять именно прошедший проверки артефакт, не пересобирать его из другой версии кода.
- [ ] Разделить сборку недоверенных PR и подготовку доверенного выпуска; PR не получает ключи публикации или подписи.
- [ ] На первом этапе оставить подписание Android на компьютере владельца; проверять сертификат, увеличение versionCode и SHA-256 готового APK перед публикацией.
- [ ] Облачное подписание APK рассмотреть отдельно, после определения защиты и резервного хранения ключа подписи.

Готовность: каждый веб-выпуск и APK однозначно связаны с исходниками и результатами проверок.

## Этап 3 — публикация после подтверждения

- [ ] Проверить тариф и видимость репозитория: доступность Environments и required reviewers различается. При отсутствии нужной защиты оставить независимое подтверждение на сервере; ручной запуск workflow не считать равноценным барьером.
- [ ] Разработать отдельный проверенный механизм публикации с ограниченным доступом. Привилегированная часть принадлежит root и не изменяется CI или пользователем доставки.
- [ ] Запретить параллельные выкладки; проверять допустимый коммит и артефакт до переключения.
- [ ] Перед выпуском создавать и проверять резервную копию, сохранять прежний код, веб-сборку и APK.
- [ ] Миграции просматривать отдельно, запускать административным wrapper строго по согласованным путям. Несовместимые изменения схемы требуют отдельного плана и окна обслуживания.
- [ ] Сохранить read-only runtime, ограниченные роли БД и MinIO, полный набор Compose overlays и права чтения исходников. Не очищать кеш в обслуживающем контейнере.
- [ ] Проверять HTTP, авторизацию и защиту контейнера после переключения. APK публиковать только после готовности API.
- [ ] При ошибке возвращать код и артефакты; не выполнять автоматический откат миграций с удалением пользовательских данных.
- [ ] Сначала проверить успешную выкладку и сценарий отказа/отката в изолированном окружении без реальных пользовательских данных.

Готовность: подтверждённый выпуск воспроизводимо публикуется, а отказ проверок приводит к безопасной остановке или откату. Ручная приёмка на телефоне сохраняется.

## Обязательные ограничения безопасности

- Не устанавливать self-hosted runner на production.
- Не передавать в GitHub production .env, административный SSH-ключ, пароли баз или Telegram-токены.
- Для доставки выделить отдельный ограниченный доступ; не предоставлять произвольный sudo, Docker socket или выполнение изменяемых из репозитория скриптов от root.
- Минимизировать разрешения GITHUB_TOKEN и других учётных данных; сторонние Actions закреплять полными SHA.
- Защитить GitHub-аккаунт двухфакторной аутентификацией, основную ветку и изменения workflow; проверить обращения с секретами и логи.
- Компрометация репозитория или workflow остаётся риском: опубликованный вредоносный код может читать данные, доступные runtime. Ограниченные права уменьшают ущерб, но не устраняют этот риск.

## Что не меняется при записи плана

Workflow и автоматическая выкладка пока не включаются. Разовый scripts/deploy-atz-release.py не превращать в универсальный updater и не запускать повторно для следующих выпусков.

Основание: [безопасность GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use), [доступность защиты environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). Доступность функций перепроверить при внедрении.
