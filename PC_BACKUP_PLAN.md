При потере ПК вместе с ключом эта копия тоже теряется. Если появится доступный
отключаемый носитель — дополнительно сохранить на нём архивы и отдельно ключ.
Шифрование backup не защищает данные от захвата работающего ПК с доступом к ключу.

## Ручной инструмент

`scripts/pull-postgres-backup.py` использует установленную Python cryptography.
Fernet подходит для этой маленькой копии; обрабатывает сообщение в памяти,
поэтому размер dump ограничен 32 МиБ. Это не инструмент для больших файлов/
полных volumes. [Документация Fernet](https://cryptography.io/en/latest/fernet/).

Загрузка требует SSH-ключа и интерактивного sudo-пароля; пароль не сохраняется.
Берётся уже проверенный неизменный dump, а не автоматически создаётся новый.
Источник и ожидаемый hash нужно брать из нового restore report:

```bash
python3 scripts/pull-postgres-backup.py \
  --source /root/arm-backup-check-20261030T153858Z/postgres.dump \
  --sha256 dff6c0491e634c329a3c9d7a35f4ea41021b6b145c5305315c13a8f8ef264bf0
```

Проверка существующей копии без записи plaintext:

```bash
python3 scripts/pull-postgres-backup.py \
  --verify-file /Users/vyacheslavandreevich/.tch15-arm/backups/postgres-20261030T155434Z-b9be3147.dump.fernet \
  --sha256 dff6c0491e634c329a3c9d7a35f4ea41021b6b145c5305315c13a8f8ef264bf0
```

При восстановлении на чистом компьютере сохранить ciphertext и recovery.key,
установить cryptography и получить plaintext через `Fernet(key).decrypt(token)`
в приватный файл 0600, затем проверить SHA-256 и pg_restore в отдельной БД.
Не восстанавливать поверх production без отдельной процедуры. Сам ключ в примерах
не указывать; читать его из приватного файла. Потеря ключа делает копию недоступной.

## Предлагаемый план полного автоматического backup

1. Состав набора: PostgreSQL + MinIO objects/metadata + пользовательский storage +
   нужные прикладные таблицы ClickHouse + секреты/конфигурация. Технические system
   logs ClickHouse и кеши не превращать в архив на месяцы. Нужен согласованный
   recovery point PostgreSQL/объектов: отдельно спроектировать сохранение версий
   или краткое ограничение записей. Production сейчас не останавливался.
2. Для больших архивов — потоковое шифрование с публичным ключом получателя;
   закрытый ключ только на Mac. Текущий Fernet-скрипт для больших архивов не расширять.
   Архив содержит manifest, commit, image digests, схемы и проверенные checksum.
3. На сервере — подготовка законченного архива root-owned инструментом с отдельным
   расписанием и ограниченным staging. Принимать только завершённые архивы;
   не открывать произвольное чтение root-файлов через sudo.
4. На Mac — отдельный SSH-ключ только для получения копий через ограниченную команду/
   пользователя. Не давать этому ключу shell/root, а production — доступ к Mac.
   Секреты sudo в plist/env/скриптах не сохранять. Сначала проверить отказ лишних команд.
5. Затем launchd на Mac: предлагать запуск раз в час при доступности компьютера и
   интернета; не требовать, чтобы он был постоянно включён. Не считать пропущенные
   интервалы выполненными, не будить компьютер без отдельной настройки владельцем.
6. Начальная политика: новые версии сохранять отдельно, не синхронизировать удаления
   с production. Предложение — 30 ежедневных наборов, лимит места и предупреждение
   о давно не полученной копии. Автоочистку включать лишь после проверки и согласования;
   текущая единственная копия не удаляется. Реальный RPO зависит от доступности Mac.
7. Пробное полное восстановление из копии на ПК, включая PDF, права доступа и
   прикладную аналитику. Только после этого считать весь backup-процесс готовым.

До реализации пунктов 1–7 автоматических копий нет; сделана одна ручная копия БД.
Платные услуги не нужны для этого варианта. Второй независимый носитель остаётся
желательным, когда он станет доступен.
