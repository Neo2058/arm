# Исполнительская дисциплина

Модуль ARM запущен на production 23 октября 2026 года. Отчёт: [deployments/2026-10-23-discipline.md](deployments/2026-10-23-discipline.md). Использует пользователей ARM; SQLite searching и Node.js API Todo для работы веб-модуля не требуются.

## Пользователи и доступ

- `tormoznik` — создаёт карточки для выбранных действующих инструкторов или для всех, видит и проверяет исполнение своих карточек.
- `nachalnik` — создаёт карточки, видит и проверяет все карточки этого экземпляра ARM, включая выданные тормозником.
- `instructor` — видит только назначенное ему исполнение, отправляет ответ и приложения, получает решение.
- Остальные роли не получают доступ к модулю автоматически. Администратор ARM назначает новые роли через существующий раздел пользователей.

Предполагается один экземпляр ARM для одного подразделения. Междеповское разграничение не реализовано: `nachalnik` видит весь модуль, а «всем» означает всех активных пользователей с ролью instructor в этой базе. Номер колонны сохраняется на момент назначения для отображения, но сам не предоставляет полномочий.

Панель руководителей: `/discipline-admin/discipline-monitor`. Это отдельная панель Filament с общей сессией ARM и только страницей исполнительской дисциплины. Новые роли не получают доступ к `/admin/users`, документам админки, настройкам и общим административным виджетам. Вход через обычную страницу ARM направляет руководителя в модуль; после устройства и барьера переход из главного меню также возвращает в модуль.

Инструктору доступна ссылка «Исполнительская дисциплина» в журнале и его боковом меню; адрес `/discipline`.

## Карточки и отчёты

Карточка содержит название, задание, срок включительно и требования: текст, файл отчёта, файл объяснения. Список исполнителей фиксируется при создании. Новый инструктор не добавляется автоматически в ранее выданные карточки. Для каждого исполнителя создаётся отдельная запись со своим состоянием и историей.

Состояния: ожидает отчёта → на проверке → принято; при возврате — на доработке → на проверке. Возврат требует комментария. Принять либо вернуть можно только последний ещё не проверенный отчёт. Отправка отчёта сама по себе не завершает поручение. Принятое исполнение закрыто для новых сдач.

Изменение/удаление выданных карточек через интерфейс не предусмотрено: условия, требования и история остаются неизменными. Старые личные `journal_tasks` продолжают работать независимо.

Изменения транзакционны; запись исполнения блокируется на время сдачи/проверки, версия защищает от устаревших решений. Ключ операции защищает от повторной обработки того же запроса; изменение содержимого при повторе того же ключа даёт 409, устаревшая версия — 412. Права и активность перечитываются из БД, в том числе при Livewire-действиях.

## Постоянный мониторинг

Панель автоматически опрашивает сервер каждые 15 секунд, пока открыта и активна; Livewire может уменьшать частоту в фоновой вкладке. Отображаются последние 30 поступивших отчётов, исполнитель, время, номер попытки, решение, непрочитанные события и сводные счётчики по всем состояниям и просрочкам. Есть фильтры по карточке и состоянию, список исполнителей с пагинацией. Полная история доступна внутри исполнения. При потере соединения появляется сообщение.

Время отображается в `DISCIPLINE_TIMEZONE` (по умолчанию Europe/Moscow); срок включает весь выбранный день в этом часовом поясе.

Внутренние уведомления создаются в PostgreSQL в одной транзакции с действием и отмечаются прочитанными при открытии исполнения. При сдаче адресаты — автор карточки и действующие начальники; при выдаче и решении — исполнитель. Отображение поступивших отчётов читает PostgreSQL напрямую и не зависит от очереди или ClickHouse.

Настройка существующей очереди ARM `deferred` не меняется. Новые события `discipline.create`, `discipline.submit`, `discipline.review` передаются через существующий ClickHouseService после фиксации операции. Внешняя доставка по email/Telegram, отдельный outbox/worker для неё и push через WebSocket в этот модуль не включены. Для мониторинга внутри открытой панели они не требуются.

## Вложения

PDF, JPEG и PNG, до 10 МиБ на файл, максимум пять файлов и 25 МиБ суммарно на сдачу. Проверяются реальный MIME и расширение, имя, размер, категории обязательных файлов и антивирус. При недоступности сканера отправка возвращает 503, отчёт не публикуется. При заражении — ошибка валидации. Файлы сохраняются приватно в MinIO в префиксе `discipline/`; в браузер выдаются через приложение после проверки доступа, как скачивание. Прямые публичные URL не используются.

Проверка файлов выполняется синхронно перед публикацией отчёта. При потере ответа повторять следует тот же запрос с теми же файлами и ключом. Браузер не умеет восстанавливать выбранные файлы после перезагрузки: полноценная офлайн-очередь для сетевого searching остаётся отдельным этапом.

При сбое между загрузкой объекта и фиксацией БД возможны бесхозные объекты. Они намеренно не удаляются автоматически: при неоднозначном результате COMMIT нельзя удалять потенциально используемые файлы. Резервное копирование и сверка MinIO/БД обязательны перед выкладкой; инструмент автоматической очистки для ARM пока не добавлен. Хранение истории ограничивает удаление связанных пользователей; используйте деактивацию.

## Запуск и выкладка

Перед миграцией существующей базы сделайте резервную копию. Не применяйте к ARM миграции Node.js Todo. Миграция модуля добавляет таблицы `discipline_*` и расширяет список ролей PostgreSQL; существующие задачи и пользователи сохраняются.

В локальной среде ARM с настроенными БД и MinIO:

```sh
php artisan migrate
npm run build
php artisan optimize:clear
```

Для файлов нужен `clamdscan` и доступный ClamAV daemon. В Dockerfile добавлен клиент. Для production Compose подготовлен отдельный overlay с ClamAV без опубликованного наружу порта:

```sh
docker compose -f docker-compose.prod.yml -f docker-compose.discipline.yml config --quiet
docker compose -f docker-compose.prod.yml -f docker-compose.discipline.yml up -d --build
# После резервной копии и проверки окружения:
docker compose -f docker-compose.prod.yml -f docker-compose.discipline.yml exec app php artisan migrate --force
docker compose -f docker-compose.prod.yml -f docker-compose.discipline.yml exec app php artisan optimize:clear
```

Сборка фронтенда требует Node.js: выполните `npm ci && npm run build` в среде сборки и доставьте `public/build` вместе с PHP-кодом. Dockerfile ARM не устанавливает Node.js.

ClamAV требует памяти и времени на загрузку сигнатур; запуск приложения в overlay ждёт его healthcheck. Настройки клиента: `DISCIPLINE_CLAMDSCAN` (путь к исполняемому файлу), `DISCIPLINE_CLAMD_CONFIG` (по умолчанию `docker/clamav/clamd-client.conf`). Для запуска без overlay укажите свой конфиг доступного clamd; отключения проверки в production нет. Проверьте ограничения PHP/Nginx и таймауты с реальными файлами до 25 МиБ.

Текущий overlay рассчитан на сеть `backend` из `docker-compose.prod.yml`; для локального `docker-compose.yaml` с сетью `arm` нужна соответствующая настройка сети ClamAV. На действующем production добавлен локальный runtime-overlay с закреплённым digest ClamAV; состав Compose и образ приложения сохранены в серверной `.env`. Используйте полный состав файлов, описанный в отчёте о выкладке.

Откат миграции удаляет данные модуля; перед ним нужна резервная копия. Если есть пользователи с новыми ролями, откат отказывается работать до явного переназначения ролей.

## Проверки

```sh
php artisan test --filter='DisciplineTest|DisciplineScannerTest'
php artisan test
npm run build
```

Feature-тесты используют отдельную тестовую БД и подменяют MinIO/антивирус. Отдельный тест проверяет запуск процесса сканера, коды clean/infected/error и отсутствие исполняемого файла. Это не заменяет проверку настоящих ClamAV и MinIO.

Для PostgreSQL можно запускать тот же набор, переопределив `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`. Никогда не указывайте рабочую базу: RefreshDatabase очищает тестовую схему.

После миграции выделенной тестовой PostgreSQL-базы с префиксом `arm_discipline_test_` доступна дополнительная проверка гонок:

```sh
php tests/Support/discipline-concurrency.php
```

Она требует pcntl, создаёт только тестовые записи и проверяет параллельные повторы, двух проверяющих и конкуренцию сдачи/проверки.

Production проверен на PHP 8.2.32 и PostgreSQL 15: тесты, миграция на восстановленной БД, реальные MinIO/ClamAV, EICAR, сканер от имени www-data, HTTP/CSRF и восстановление резервных копий. Аккаунтов руководителей пока нет; после их создания остаётся проверить реальный вход с устройством и барьером. Сетевой API и офлайн-очередь Qt, разделение searching на два приложения выполняются отдельно.
