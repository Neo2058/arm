## Выявленные проблемы расчёта (по коду, без изменения формул)

1. WorkShiftController.preview использует PayrollService с PREMIUM=0.32; store также вызывает его,
   но возвращаемые minutes/earnings не совпадают с сохраняемыми total_minutes/estimated_earnings.
   Saving hook WorkShift заново вычисляет стоимость work по фиксированной ставке 450 без премии.
   Пример: 8 часов без перерыва/надбавок — preview 4752, модель 3600. Это арифметическое
   расхождение двух путей, не утверждение о правильной зарплате сотрудника.
2. DeviationCalculator.calculate(array $shift) читает неопределённую $data, использует 8 часов
   по умолчанию и коэффициенты строковых типов; модель берёт default_minutes/hourly_rate из каталога.
3. Валидация смен допускает отсутствие дат для work, отрицательный перерыв и не требует ended_at > started_at.
4. updateOrCreate использует user_id + shift_date: повторная запись на тот же день заменяет прежнюю;
   поддержка нескольких фактических смен в сутки требует отдельного решения и миграционного анализа.
5. Календарь суммирует total_minutes всех записей. Нужно явно различать фактическую работу,
   оплачиваемые отвлечения, общую продолжительность присутствия и перерывы.
6. Проверить граничные случаи Carbon/timezone/округления, соседние месяцы и пересечения.
   Полный числовой прогон и бухгалтерская сверка ещё не выполнены.

## Предлагаемая последовательность

### Этап 1. Правила и эталонные примеры учёта (первый приоритет)

- Утвердить источник ставок, премий и надбавок; отдельно определить предварительную оценку и
  официальный расчёт. До этого не выбирать автоматически ни 450, ни 450×1.32.
- Получить обезличенные примеры с ожидаемыми часами/суммами; уточнить, что показывается:
  начисление до удержаний, сумма на руки или ориентировочная стоимость смен.
- Утвердить правила перерывов, перехода суток/месяцев, округления и учёта отвлечений.
- Уточнить категории работников и утверждённые нормы отдыха/длительности смены.
  Фактический интервал между окончанием и следующим началом можно считать независимо от норм;
  статус «нарушение» нельзя выдавать по придуманному универсальному порогу.
- Отдельно согласовать несколько смен в сутки, корректировки и исторические тарифы.
- Закрепить тесты preview = сохранение = повторное чтение, totals и эталонные примеры.

### Этап 2. Один расчёт на сервере для веба и APK

- После утверждения правил устранить противоречие PayrollService и WorkShift::booted(),
  сохранив единственный согласованный механизм заполнения precomputed полей.
- Время считать в целых минутах; деньги считать без накопления float-ошибок с явным округлением.
- Валидировать даты/таймзону/перерывы/пересечения, проверять принадлежность записей пользователю.
- Согласовать дату применения тарифов. Не пересчитывать все исторические смены при простом просмотре.
- Официальный контур /uchet (FoxPro/ЛС) не подменять личным WorkShift-календарём.
  Сверять необходимые показатели через существующие сервисы, не заводить параллельный бухгалтерский расчёт.
- Проследить границы месяца и предыдущую/следующую смену, чтобы отдых считался за пределами выбранного месяца.

### Этап 3. Мобильный раздел рабочего времени

- Sanctum API на существующих данных, отделённый от session/CSRF web routes.
- Календарь и список смен; карточка с началом/окончанием, полной продолжительностью,
  перерывом и зачтёнными рабочими минутами.
- Предыдущая/следующая смена, фактический отдых и понятные предупреждения по утверждённым нормам.
- Месячная сводка фактических/оплачиваемых часов, отвлечений, нормы и отклонений — если есть источник нормы.
- Детализация суммы: часы, применённый тариф, надбавки и округление; не только итоговое число.
- Создание/корректировка/удаление только после определения web parity и полномочий;
  повторная отправка не должна удваивать записи или терять смены.
- Первым релизом закрыть учёт времени и эталонную сверку, не маскировать нерешённые расчёты красивым UI.

### Этап 4. Навигация, все иконки и доступ по ролям

- Общая карта возможностей на сервере; UI скрывает недоступные пункты,
  API независимо проверяет права. Новые роли не вводить.
- Не добавлять бесконечные нижние вкладки: вынести полный каталог в «Разделы»,
  наиболее частые действия доступны непосредственно и зависят от роли.
- Единый согласованный набор векторных иконок, подписи, контраст, active/inactive состояния,
  достаточная область нажатия и доступность. Без случайной смеси эмодзи и разных стилей.
- Отдельный эскиз launcher/adaptive icon с учётом масок Android; утвердить до финальной сборки.
- Каноничную веб-карусель не менять; мобильную навигацию не превращать в её обязательную копию.

### Этап 6. Проверки, сборка, выкладка

- Тесты изоляции пользователей и ролей для каждого нового API.
- Для расчётов: переход через полночь/месяц, перерывы, нулевая/некорректная длительность,
  пересечения, интервалы отдыха, исторические ставки, отвлечения, точность месячной суммы.
- Веб и APK показывают одинаковые результаты на одних входных данных.
- Существующие обязательные feature-тесты доступа, JS tests, native release и smoke на Android.
- Работа с плохой сетью, повторными запросами и доступностью UI на слабом телефоне.
- Подписанный APK с повышением versionCode через проверяемую публикацию, backups и безопасный откат.
- Новые ClickHouse-события и изменения финансовых формул согласовывать до реализации.
